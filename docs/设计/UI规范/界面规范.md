## 2. 设计定位（信息架构原则）

**产品形态**：Web 网站优先（桌面 + 响应式），**内容型垂直社区**，单校范围（[技术方案](../tech-design.md) 第 1 节）。

由此确定的**三条硬约束**：

1. **信息密度优先，列表页是主战场**。用户 80% 的时间在扫列表，判定列表页好坏的标准是"一屏能扫几条、每条能否看清是否值得点"，不是视觉张力；
2. **内容为主体，装饰为零**。不做插画、不做渐变、不做大圆角卡片堆叠——这些会挤掉列表的信息密度；
3. **导航服从"版块少、层级浅"**。当前 6 个固定版块（`qna` / `resources` / `interview` / `contest` / `course` / `chat`，见 [PRD](../../requirements/prd.md) F-FORUM-001）。

| 决策 | 结论 | 理由 |
|---|---|---|
| 顶栏平铺 6 版块 | ✅ **保留现状** | 6 个固定版块顶栏放得下；`overflow-x: auto` 已处理窄屏 |
| 首页版块卡片矩阵 | ✅ **保留现状** | `el-col xs=24 / sm=12 / md=8` 响应式已就位 |
| **左侧版块导航栏** | ❌ **本阶段不做** | 左侧栏的价值在"版块多 + 有二级导航（我的 / 收藏 / 设置）"。6 个版块 + 试点期流量撑不起，且与 [CR-022](../../change-log.md) 最小 MVP 相悖。**重新评估的触发条件**：版块数 > 10，或个人中心落地后需要常驻二级导航 |
| **面包屑** | ✅ **已补（v1.3，[CR-025](../../change-log.md)）** | 原判"⚠️ 建议补（P1）"——现状从首页 → 版块 → 帖子三级跳转后，页面内没有任何"我在哪"的信息。**v1.3 状态回填**：版块页 / 帖子详情页已补面包屑（`el-breadcrumb`，首页 → 版块 → 帖子），[CR-025](../../change-log.md) 批次 2 / 批次 3 落地 |

## 4. 设计令牌建议

### 4.1 落地方式

**新增 `frontend/src/styles/tokens.css`，在 `main.ts` 中一次性引入**（纯 CSS 自定义属性，**不引入任何构建依赖**）。

> **加注偏离（v1.1，[CR-023](../../change-log.md)，2026-09-12）——本条已被推翻，原文保留**：落地方式按本条执行（`tokens.css` + `main.ts` 一次性引入），**但"不引入任何构建依赖"这条限制被 [CR-023](../../change-log.md) 推翻**——同时引入了 `tailwindcss` + `@tailwindcss/vite` 两个 devDependencies 作为**样式工具层**（Element Plus 仍是唯一组件库，未换栈）。**后果（已在 CR-023 登记为最大技术风险）**：Tailwind v4 产出**分层**样式（`@layer`），而 EP 样式**未分层**，**未分层样式恒胜分层样式**，故**工具类无法覆写 EP 组件内部样式**。由此形成的边界约定：**EP 组件一律走 CSS 变量（在 `tokens.css` 用 `:root:root` 覆写），自有元素才用工具类**；该边界**无 lint / 测试强制**，靠 `AGENTS.md` 的人工约定。

**与 Element Plus 的关系**：不另起一套平行体系。Element Plus 已用 `--el-*` 定义主色、圆角基数等，**已有的一律复用，只补它没有的**（间距刻度、阅读列宽、元信息文本色、分隔线色）。必要时以映射方式覆写，例如 `--el-text-color-regular: var(--cl-text-regular)`。

> **加注（v1.1，[CR-023](../../change-log.md)）——本条被完整执行且加强了**："不另起平行体系"已落实；覆写不止于"必要时映射"，而是**成批覆写**（主色与 `light-3/5/7/8/9`、`dark-2`、六档字号、`--el-border-width` 等），全部集中在 `tokens.css` 一处。**一处刻意的例外**：`--el-box-shadow-light` **不覆写**——下拉菜单 / 消息提示等浮层仍需阴影表达层级（去阴影只针对卡片，经模板 `shadow="never"` 归零）。

### 4.3 对比度实测（WCAG 2.1 AA）

按 WCAG 相对亮度公式计算（数值经脚本复核，非目测）：

| 前景色 | on `#f5f6f8`（页面底） | on `#ffffff`（卡片） | 结论 |
|---|---|---|---|
| `#303133` | 12.04:1 | 13.02:1 | ✅ 达标 |
| `#606266` | **5.65:1** | **6.11:1** | ✅ 达标（**元信息应改用此色**） |
| `#909399` | **2.85:1** | **3.08:1** | ❌ **不达标**——现状 `.post-meta` 用的就是它 |
| `#a8abb2` | 2.13:1 | 2.30:1 | ❌ 仅可用于占位符 / 禁用态 |
| `#409eff` | **2.57:1** | **2.78:1** | ❌ 一般不达标——见下 |
| `#337ecc`（Element Plus `primary-dark-2`） | 3.89:1 | 4.20:1 | ⚠️ 仍差一点 |
| **`#1a6fc4`** | **4.72:1** | **5.10:1** | ✅ 达标（**建议作正文链接色**） |
| `#185FA5` | 6.03:1 | 6.52:1 | ✅ 达标（更保守的选择） |

**由此得到两条硬约定**：

1. **元信息、摘要等 ≤14px 文本不得用 `#909399`**，用 `#606266`；
2. **`#409eff` 不得作为小号文字色**。现状 `#409eff` 被用在列表标题 hover、版块链接（13px）等多处——按 AA 口径**不达标**（正常文本要求 ≥ 4.5:1；仅 ≥18.66px 粗体或 ≥24px 时可放宽至 3:1）。**保留 `#409eff` 给按钮底色，文字链接改用 `#1a6fc4`，或在链接上叠加下划线以不依赖颜色区分**。

> **加注（v1.1，[CR-023](../../change-log.md)，2026-09-12）——数据表与两条硬约定的结论全部仍然有效，只是达成方式变了**：
>
> ① **上表的对比度数值无需重算**（公式与数值经脚本复核，`#909399` 2.85:1 / `#606266` 5.65:1 / `#409eff` 2.78:1 等仍然是判断依据）；它在 v1.1 的作用是**历史依据**——现在主色已不是 `#409eff`。
> ② **硬约定 1 已落地**：`#606266` 被采纳为 `--cl-text-meta`，元信息 / 摘要不再用 `#909399`（实测元信息色 5.65:1 ✅，即 §3 第 5 项收敛）。
> ③ **硬约定 2 的达成方式改了**：本 CR **没有**改用 `#1a6fc4`，而是**把主色整体换成 `#0f766e`**——于是"主色作小号文字"**本身就达标**（白底 5.47:1、对页面底 5.06:1），文字链接直接用主色。**原写的"保留 `#409eff` 给按钮底色"因此失效**（主色已不是它）。
> ④ **本 CR 复核时发现本条未覆盖的一处对比度问题（已修）**：**实心主色按钮的 hover 底色**由 EP 默认取 `--el-color-primary-light-3`（主色掺白 30%），**白字压在其上只有 3.08:1 ❌**——已改为主色派生深色（实测 `rgb(13.5,106,99)`，**6.44:1 ✅**）。**这条不在 §4.3 原表里**（原表只覆盖"文字色 on 底色"，未覆盖"组件状态色"），补记于此，供后续新增交互态时照此口径自查。
>
> **一处渲染层的如实标注（与对比度无关，但同属本表所说的"视觉正确性"）**：**0.5px 边框的取值依赖设备像素比**——**真机 DPR=2（Chrome 150）实测计算值就是 `0.5px`**；而**无头 Chrome 的 `deviceScaleFactor` 模拟不驱动边框对齐**（模拟 1/2/3 一律报 1px、0.25/0.5/1px 像素带相同，**属仿真假象，不得作为证据**）；**DPR=1 屏上会被钳到 1px**（视觉为更浅的细线），**未做多设备验证**。
>
> **v1.2 补注（如实更正：同 §4.2，§11 的 v1.2 条目声称本表"已追加加注"而实际漏写，本注为 v1.3 期间补落笔）**：**上一条 v1.1 加注的 ③ 被 [CR-024](../../change-log.md) 撤回**——"主色整体换成 `#0f766e`、主色作小号文字本身就达标"**不再成立**；主色回到 `#409eff` 后，**硬约定 2 恢复本表原始达成路径**：保留主色给按钮底色，**小号文字 / 链接改用独立的 `#1a6fc4`**。② 硬约定 1（元信息用 `#606266`）**不受影响**，继续有效。④ 与渲染层标注**不受影响**。
>
> **v1.3 状态回填（[CR-025](../../change-log.md)，发起人决策后落地）**：**硬约定 2 的达成路径已在代码中兑现**——`#1a6fc4` 独立于主色写入 `tokens.css`，**8 处小号文字 / 链接已切换**（[CR-024](../../change-log.md) 只改了定义值、消费端未动，是 CR-025 补的）。**两处知情接受的例外（不是遗漏，已在 CR-024 / CR-025 登记）**：① **品牌字样（logo）仍用主色 `#409eff`**——WCAG 对 logo / 品牌名不计对比度要求；② **白字压实心主色按钮（2.78:1）知情接受**——主色回退时已明确以设计稿为准。本表**数据行不重算**（它们是判断依据，与主色取值无关）。

### 5.1 列表项（`PostListItem.vue`，建议新增）

| 空 | **一句话文案 + 主色按钮（v1.3 起；原为 `el-empty`）** | ✅ 已实现（"还没有帖子，来发第一帖吧" + 发帖按钮） | 文案必须给出下一步动作，不能只写"暂无数据"。**v1.3 偏离（[CR-025](../../change-log.md) 批次 2 已登记）**：载体从 `el-empty` 改为**纯文案 + 按钮**，依据是设计系统页"**插画为零**"——`el-empty` 自带插画，与新设计稿冲突 |

>
> **v1.3 状态回填与一处偏离（[CR-025](../../change-log.md)）**：加载态**两处**与空态**一处**见上表（均已按设计稿落地）；**错误态与 3001 态两份实现未被 CR-025 改动**——`el-alert` 内联重试与 3001 专用 `el-result` 原样保留。**偏离的处置口径**：空态载体换掉 `el-empty` 是**对本文约定的偏离**，已随 [CR-025](../../change-log.md) 登记为**实施偏差①**，此处标注为设计稿驱动的**有意更换**，非退化——**若后续页面（如搜索 / 通知）要复用空态，沿用"文案 + 按钮"写法并保证文案给出下一步动作**。

### 5.3 表单与草稿

- **提交失败不得清空已输入内容**（现状 `PostDetailView` / `PublishView` 均已满足——失败时保留 `replyMd` / `form`）；
- 提交中按钮必须进 `loading` 且禁二次提交（现状已满足）；
- 校验顺序：**前端先做非空校验给出提示，最终以后端校验为准**（后端 `1001` 为参数错误）。

### 5.4 分页

- **参数口径：`page` / `size`**（`page` 从 1 起）。这是本 Sprint 确认为实现口径的写法，技术方案 §5 已同步（原 `pageNum` / `pageSize` 口径作废，见 [sprint-2-design.md](../../development/sprint-2-design.md) §6 的 D-6）；
- 每页条数：**首页 10、版块页 20、楼层 20**（现状值，保留）；
- 列表页用 `layout="prev, pager, next"` 居中；**仅在 `total > size` 时渲染**分页器（现状已满足）。

### 5.5 时间显示

- 传输：ISO-8601 UTC；展示：前端本地化（`utils/time.ts` 的 `formatTime`，输出 `YYYY-MM-DD HH:mm`）；
- **建议（P1）**：列表页改用**相对时间**（`3 小时前` / `昨天`），详情页保留绝对时间。列表页的绝对时间对扫读帮助有限，而"多久之前"直接回答"这条热不热"。

> **v1.3 状态更新（[CR-025](../../change-log.md)）——本建议已落地（P1 → ✅）**：`utils/time.ts` 新增 `formatRelativeTime`（**刚刚 / N 分钟前 / N 小时前 / 昨天 / 前天 / N 天前，超过 7 天回退绝对时间**），**首页 / 版块列表的帖子时间改用它，详情页与楼层保留 `formatTime` 绝对时间**——分工与上条建议完全一致。**一处随设计稿的呈现细节**：列表元信息各段之间用「·」分隔（作者 · 回复数 · 相对时间）。

### 5.6 Markdown 正文与代码高亮

**这是 ADR-005 的硬边界，前端不得越界**：

| 项 | 约定 |
|---|---|
| 渲染位置 | **只在服务端一个执行点**（`common/markdown`）。发布时渲染 `content_html` 落库，请求时**零渲染** |
| XSS 防线 | 在服务端的 `MarkdownRenderer`（flexmark + jsoup 白名单），**不在前端**。前端只负责 `v-html` 呈现 |
| **禁止** | 前端二次渲染 Markdown 做正文展示；前端自行拼接 HTML |
| 代码高亮 | **由前端 `highlight.js` 完成**（服务端只输出 `<pre><code class="language-*">`，避免为 hljs 的样式类扩大白名单）——**当前未实现，属欠账** |
| 样式归属 | `.markdown-body` 必须**提为全局样式**（现状写在 `PostDetailView.vue` 的 `scoped` 中，**发帖预览无法复用**） |

> 代码块样式最低要求：`background: var(--cl-bg-code)`、`--cl-radius-sm`、`overflow-x: auto`、行内 `code` 用等宽字体；**长代码必须横向滚动而非换行**。
>
> **v1.1 更新（[CR-023](../../change-log.md)）**：**"样式归属"一行已落地**——`.markdown-body` 已从 `PostDetailView.vue` 的 `scoped` 提为**全局内容排版**（消费令牌，供后续发帖预览复用），手写字号 / 颜色改为消费 `--cl-*`；**代码块样式最低要求已在真实帖子中逐项实测通过**（背景、圆角、`overflow-x: auto`、等宽行内 `code`）；**文字链接改用主色 `#0f766e`**（不再是 `#409eff`）。**仍未做**：**`highlight.js` 依然没有引入**——服务端输出的 `class="language-*"` 目前没有任何前端着色，**ADR-005 的欠账未兑现**（§3 第 8 项、§9.1 P0 第 4 项仍开放）。

### 5.7 鉴权与跳转

- 受保护路由（`/publish`、`/notifications`）由路由守卫统一拦截，未登录跳 `/login?redirect=<原路径>`（现状已实现）；
- 页面内触发受保护操作（如发回复）**必须二次判断登录态**并携带回跳，不能只依赖路由守卫——因为详情页本身是公开的；
- **前端显隐只是体验，不是安全边界**：真正的鉴权在后端。当前 `SecurityConfig` 仍为 `permitAll()`（**N-4 敞口**，归口 A3-9），受保护端点靠**手写校验 + 401 单测**顶住——前端**不得**因"后端没拦"而省略登录态判断，也不得因"前端拦了"而认为安全。
