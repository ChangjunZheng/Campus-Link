## 0. 评审方式（⚠️ 一处必须如实登记的流程偏离）

- **指令原文**（发起人 2026-09-19）：「**你可以进行前端开发（我没有说你一直不能动前端），现在`评审七份增量 PRD 草案` 没有问题后就开始实施**」。
- **评审主体**：由 **AI 协作会话执行**，发起人授权并当日追认。**这里有一条比 W-01 更弱一档的事实，必须写下来而不是含糊过去**：七份草案中有六份由 AI 会话起草，本轮又由 AI 会话评审——**起草侧与评审侧没有第二双眼睛**。[W-01](../流程偏离记录.md)（评审无外部参与者、以"异步书面评审"补偿）签署时描述的是"无外部参与者"，本纪要的情形是"**评审人即起草人所属的同一侧**"，补偿② 的"外部性"在本轮**为零**。
- **因此本文的效力边界**：它**能**作为"需求已逐条核对过代码事实"的记录，**不能**被读成"已经过独立评审"。若将来补做人工评审，本纪要逐条可推翻。
- **"经正式变更评审"仍 0 次**（手册 4.2 要求评估后同步产品 / 开发 / 测试 / UI 四方，单人项目无第二角色可同步）。
- **同轮解除的一条限制**：`frontend/` 不再归并发会话独占（发起人本轮明示）。受影响的是 F-ACC-007 草案 N12 与"两轮制声明"——见 §5。

## 2. 评审查出的两条不利事实（草案自己没发现，实施轮必须知道）

1. ⚠️ **「学号前两位 = 入学年份」是循环取证**。CR-036 `:26` 用"如 `249971346` → 2024 级"作证据，而该学号出自**本仓自造测试夹具** `InMemoryTestRosterGateway.java:25`；真实名册从未到位（B1 未交付），`StudentId.java:10` 只校验 `\d{9}`、无任何年份语义。后果在现有开发库上可量级复现：45 个合成学号前缀全为 `88880`（`D001__seed_dev_roster_45.py:66`）→ 落在草案自设的 20~31 区间**之外** → **届徽章一个都不渲染**，任何"覆盖率 100%"式的真机验收在现有数据上根本做不出来。**更坏的一侧没有被这道闸挡住**：若真实编码的前两位是院系 / 校区码而恰好落进 20~31，页面会**自信地显示错误的届**，平台无感知。
   ⇒ **本轮处置**：F-ACC-007 的届徽章**必须带区间兜底**（草案 §3.2 已写"前两位不在 20~31 → 不显示"，本轮照做并补一条单测），且**推导值不落库**；CR-036 本体仍不排期。
2. ⚠️ **CR-067 草案 §4.3 的契约增量数字算错**：原文"路径 21 → 22"，实测 `GET /posts/mine` 与 `GET /replies/mine` **各是一条新路径** ⇒ 应为 **21 → 23**；且 schema 至少 +2（`ProfileUpdateCommand` 与"我的回帖"条目 VO）、tag 可能 9 → 10，草案均未列。实施轮以**重抓后的实测**为准，不沿用草案数字。

## 5. 本轮排期决定

- **实施 CR-071 ＝ F-ACC-007 第一轮**（唯一"评审通过且当场可做完并测完"的一支）。
- **N12 与两轮制声明据实作废一半**：`frontend/` 本轮解锁 ⇒ 设置页、两个"我的"列表页、顶栏入口**并入第一轮一起做**，草案 §4.3 五条"依赖前端不签"里**有两条本轮即可签**。⚠️ 但**不把"两轮并一轮"写成发起人的需求变更**——它是限制解除的自然结果，登记在此即可。
- **实施顺序锁死，不可并行**（三方抢同一处代码：`users` 表 + `Account` 聚合 + `PUT /users/me`）：**CR-067 第一轮 → CR-036（随主页本体）→ CR-042（顺带）**。若 CR-042 硬挤在前面，其 `V3` 迁移号会与 CR-067 的 `V3__my_content_indexes.sql` **撞号**。
- **CR-033 的纯检索版**列为**下一功能候选**（依赖链：`F-007 标签闭环 → F-AI-001a → 埋点基线 → 语义版 → F-AI-002 → F-AI-003 →（≥500 帖）F-AI-004`；唯一自洽起点是 F-AI-001a，且开工前须先答其 Q1 阈值与 Q4 埋点方式）。

## 6. 本轮新登记的一条缺口

**"大模型 / embedding 服务商"是一条从未被登记过的决策项**——[部署与机审选型决策材料](部署与机审选型决策材料.md) 只有两个决策点（部署形态 `:18`、机审服务商 `:40`），**不覆盖 AI 服务商**；技术方案全文 grep `LLM|大模型|embedding|向量|module/ai` **零命中**，ADR-001~012 无一条涉及，CR-033 §9 自己写下"视需要新增 ADR-013"但**未写**。⇒ 已按[问题清单](../项目现有问题清单.md)的编号规则新登记一条敞口（见该清单本批版本行），**不在本轮处置**。

**顺带澄清一条常被混用的判据**：向量检索 / MeiliSearch **与现有 ADR 无冲突**（ADR-004 已为 P1 预留 MeiliSearch、只排除 ES，见 `技术方案.md:365`），"要先改 ADR 才能上检索"是不成立的说法；真正缺的是**服务商与密钥注入**那一层。
