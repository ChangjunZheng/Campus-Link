## 1. 目标

兑现 [PRD](../../需求/产品需求文档.md) **F-FORUM-006「删除自己的帖子」（P0）** 的**后端一半**：作者本人可通过 `DELETE /api/v1/posts/{id}` 删除自己的帖子，删除后**前台所有位置不可见**，操作**留后台审计日志**；闭环[项目现有问题清单](../../项目现有问题清单.md) **F-004**（当前 `PostController` 无 `@DeleteMapping`、无删除用例）。

**本 CR 不声称 F-FORUM-006 整项完成**——前端入口与"计数回收"两条见 §2「不做」，各自登记为缺口。

## 2. 范围

- **做**：
  1. 端点 `DELETE /api/v1/posts/{id}`：**受保护**（`@SecurityRequirement` + `CurrentUser.requireId`），仅作者本人；成功 `200 / ApiResponse.ok()`（无 body，同 `accept` 先例）；
  2. **软删走既有墓碑 `posts.is_deleted=1`**（V1 已建列，**零迁移**、既有两条列表索引已含该列）；
  3. 端口新增定向 UPDATE `markDeleted(postId)`——**条件带 `is_deleted=0`**，使"删除"与"读不到"同源（并发二次删除只有先到者改到行）；
  4. 审计：`AuditService.record(userId, "POST_DELETE", "posts", postId, detail)`，`detail` 只记 `boardId` 与截断后的标题，**不落正文与任何敏感明文**；
  5. 单测 + 契约快照重生成（新增 1 个 operation，diff 非空属预期）。
- **不做**（每条带理由，这一节比"做"更重要）：
  1. **不引入 `PostStatus.DELETED`**。三点取证：① 仓储读侧**已把 `is_deleted=1` 定义为"不存在"**（`PostRepository#findById` javadoc），列表 / 搜索 / 详情 / 楼层 / 收藏 / 热榜候选 / 通知摘要**七条读路径已全部过滤 `is_deleted`**，走 status 要逐条复核；② 其中 `findByIds`（通知读时组装）**不看 `status`**，只把"删除"塞进 status 会让已删帖的标题照常进通知；③ `status=REMOVED` 的既有语义是**平台处置**（`PostStatus` 注释：机审 / 管理员下架预留），与作者自助删除是两件事——混用后 F-SAFE-003 处置台落地时将**无法区分"谁删的"**。
  2. **不做管理员 / 机审删除、不做恢复入口、不做批量删除**（F-SAFE-003 未实现；行与内容仍在库，恢复见 §6）。
  3. **不级联删楼层与 `likes` / `favorites` 行**。与 [CR-060](../../变更日志/变更台账.md#cr-060) 及 `findFavoritePosts`「收藏行保留」的既有取舍一致：楼层与互动是删除后的独立事实，处置台与统计要用；前台侧已因父帖不可读而全部不可达（`listReplies` / 回帖 / 点赞 / 收藏四条入口都以 `requireVisiblePost` 开头，实测确认）。
  4. ⚠️ **不实现 PRD 的"计数回收"——本条按落码偏差如实登记，不静默放过**：实测 V1 `boards`（无 `*_count` 列）与 `users`（25 列，**同样无 `*_count` 列**）**没有任何帖子计数字段**，"回收"在现库上**没有作用对象**；帖子自身的 `reply_count / like_count / favorite_count` 随墓碑行一起从前台消失。真要做需先加计数列（连带写放大与一致性维护），属独立一批变更。
  5. **不改任何 `frontend/` 文件**（另有会话在改界面）。**如实登记后果**：删除能力仅 API 可用、页面无入口，**PRD F-FORUM-006 的用户可见验收不能签**，前端入口归后续 CR（与 [CR-058](../../变更日志/变更台账.md#cr-058) 首页双排序 UI 同一类欠账）。
  6. **不动 `hot_score`**：`resetHotScoresBefore` 的条件已覆盖 `is_deleted=1`（下轮刷新自动置零，不留高分幽灵帖）。

### 7.3 真机取证（临时端口 8099、`APP_ROSTER_BYPASS=false`、Redis 起，**8088 / 8089 与他人的 45 个测试账号数据一律未动**）

- **鉴权三态**：匿名 `DELETE` → `401 / 4001`（框架层，未进业务代码）；他人账号 → `403 / 4002`；作者 → `200`、体为 `ApiResponse`（`data` 省略）。
- **删后 11 处位置逐项实测**：全站列表 / 版块内列表 / 热榜 `sort=hot` / 站内搜索 / 详情 / 楼层列表 / 回帖 / 点赞 / 收藏 toggle / 采纳 / **我的收藏页** —— 前五读处不可见、读详情 `404 / 3001`，写侧五入口一律 `404 / 3001` 拒绝（`requireVisiblePost` 同源生效）。
- **幂等**：二次删除 `404 / 3001`，且 `audit_logs` **不新增行**（实测 `POST_DELETE` 行数不变）。
- **通知回落**：删被通知过的帖后，`GET /notifications` 该条不下发 `postId`、文案回落「内容已删除」（`findByIds` 排墓碑的既有行为，未被本 CR 破坏）。
- **库侧证据**：`posts.is_deleted=1` 单行翻转、`status` 仍 `PUBLISHED`（未动，按 §2 决策）、`hot_score` 下轮刷新归 0、`audit_logs` 出现 `POST_DELETE` 行（`detail` = `boardId=… title=…`，**无正文**）。
- **回归面**：对照帖（同版另一作者的帖）全程可读可互动，未误伤；发帖 / 回帖 / 采纳 / 点赞 / 收藏 / 搜索 / 通知 / 匿名 401 / 健康检查九条链路复跑无变化。**共 38 项断言**（37 项实质 PASS + 1 项 D-6 所述伪 FAIL）。
- ⚠️ **顺带复现一次 CR-058 的锁 TTL 陷阱**：取证期用 `HOT_REFRESH_INTERVAL_MS=20000` 缩短刷新周期，实测两轮间隔 **5 分钟**——默认 `lock-ttl-seconds=300` > 刷新周期，advisory 锁不显式释放，**实际周期被 TTL 决定**。AGENTS.md 早已写明这条，本次是首次在真机上看到它的后果（不影响本 CR 结论，"下轮置零"仍按预期发生）。
