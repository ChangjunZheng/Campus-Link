## 1. 目标

落地 PRD [F-SOC-001](../../需求/产品需求文档.md)：站内通知——帖子被回复 / 被点赞 / 被收藏、回复被采纳；未读数角标，全部已读操作。验收（PRD）：A 回复了 B 的帖子 → B 的通知列表可见未读角标；点击通知跳转对应内容。**同时闭环两笔挂起账**：CR-043（采纳）与 CR-048（点赞 / 收藏）当时登记的"通知发放挂起归 F-SOC-001"。

## 2. 范围

- **做**：
  - 新建限界上下文 `module/notification`（照抄 `module/{account,forum}` 四层范式，ADR-012；跨上下文只调对方 `application`）；
  - **零迁移**——V1 的 `notifications` 表已就位（`user_id` / `type`(reply/like/favorite/accept/quote) / `actor_id` / `target_type` / `target_id` / `is_read` / `created_at`，索引 `idx_notifications_user(user_id, is_read, created_at)` 正好覆盖三条查询）；
  - 5 个触发点（forum 侧 application 服务在动作成功后调用 `notification.application.NotificationApplicationService.notify(...)`，**自触发抑制**：actor == 接收人不产生；toggle 取消（active=false）不产生）：

    | 触发 | type | target | 接收人 | 挂点（已核实存在） |
    |------|------|--------|--------|--------------------|
    | 帖子被回复 | `reply` | `REPLY`/replyId | 帖子作者 | `ReplyApplicationService.reply(...)` |
    | 回复被采纳 | `accept` | `REPLY`/replyId | 被采纳回复作者 | `PostApplicationService.acceptReply(...)` |
    | 帖子被点赞 | `like` | `POST`/postId | 帖子作者 | `InteractionApplicationService.togglePostLike(...)` |
    | 楼层被点赞 | `like` | `REPLY`/replyId | 楼层作者 | `InteractionApplicationService.toggleReplyLike(...)` |
    | 帖子被收藏 | `favorite` | `POST`/postId | 帖子作者 | `InteractionApplicationService.togglePostFavorite(...)` |

  - 3 个新受保护端点（全部 `@SecurityRequirement` + `CurrentUser.requireId`）：
    - `GET /api/v1/notifications?unread=&page=&size=`——我的通知分页，`unread` 可选过滤；出参 `PageVo<NotificationVo>`；
    - `GET /api/v1/notifications/unread-count`——未读数（顶栏角标）；
    - `PUT /api/v1/notifications/read-all`——全部已读，返回 `{updated}`（技术方案 §5 原计划行 `GET / PUT /api/v1/notifications?unread=` 中的 PUT 由本路径取代，比照 CR-043 / CR-049 先例，实施时在 §5 加注）；
  - 通知内容**读时组装**（零加列）：`NotificationApplicationService` 组装 VO 时跨上下文调 `AccountApplicationService.nicknamesOf`（actor 昵称，已存在）与 forum 查询侧**新增两个只读方法**（`postBriefsOf(ids)` → 标题；`replyBriefsOf(ids)` → postId + floorNo）；
  - 前端：`/notifications` 由占位页转真页面 `NotificationsView.vue`（未读高亮 + "全部已读"按钮 + 分页 + 相对时间）；顶栏铃铛加未读角标（进应用取一次 + 路由切换刷新 + 30s 轮询；点击条目跳 `/post/{postId}`，楼层类通知带 `#floor-N` 锚——详情页若无锚则落到帖子，实施时核实）；
  - 契约快照再生成（v1.9）。
- **不做**：
  - `quote` 通知（引用回复 `quotedReplyId` 不在 MVP，未实现）；
  - 逐条已读（PRD 只要求"全部已读"，表结构 `is_read` 已支持，后续 CR 可加）；
  - WebSocket / SSE 实时推送（用轮询，PRD 未要求真实时）；
  - 通知设置 / 免打扰 / 邮件推送；
  - F-SAFE-003 处置通知（处置台 F-ADMIN-002/003 未实现）；
  - 新增 `ResultCode`（复用 401/4001、403/4002；无新业务错误码）。

## 7. 实施结果与偏差（2026-09-14 补记，原 §1~§6 一字未改）

**结论**：§4 六步全部完成，`mvn verify` **162 全绿**（基线 145 → +17），真机冒烟通过，快照已再生成为 **v1.9**，`/notifications` 与顶栏铃铛可用。**零迁移、零新增 `ResultCode`**（与 §2 的核实一致）。

**与计划的偏差（5 项）**：

1. **单测实际 +17 而非 §5 估的 6~8 例**——`module/notification` 15 例（`NotificationApplicationServiceTest` 7 覆盖五条触发链 + 自触发抑制、`NotificationRepositoryImplFilterTest` 3、`NotificationControllerAuthTest` 5 覆盖三端点匿名 401 与参数校验前置），另 forum 侧 `InteractionApplicationServiceTest` **+2** 例（激活时发通知 / 取消时不发）。**多出的部分是适配层与鉴权面的必要覆盖**，见偏差 2。
2. **`unread` 筛选反义缺陷（真机才暴露，计划内无人预见）**——适配器写成 `.eq(is_read, unread)`，"只看未读"被查成"只看已读"。应用层 Mockito 结构上看不见列语义（它只验"调没调仓储"），**这类缺陷只能在适配层拦**，故新增 `NotificationRepositoryImplFilterTest`：捕获 `QueryWrapper` 后用正则取出绑定值断言。改法为 `!unread`。
3. **前端判空写错（同属真机才暴露）**——`n.postId === null` 恒不成立：`spring.jackson.default-property-inclusion: non_null` 使 null 字段根本不下发，前端拿到的是 `undefined`，于是渲染出「#undefined 楼」并跳 `/post/undefined`。改为真值判断、`NotificationVo.postId` 类型改可选，并把**"后端可空字段在前端是『可选』而不是『等于 null』"** 记为通用口径（`utils/request` 与全部 VO 同此）。
4. **楼层定位改用查询参数而非 `#floor-N` 锚**——§2 预留的"若无锚则落到帖子"未发生：详情页改为读 `?floor=<replyId>` 并 `scrollIntoView` 定位高亮。**已知限制**：目标楼层不在当前分页时只落到帖子顶部（未做自动翻页定位）。
5. **快照 diff 不是纯新增**——`git diff` **322 增 / 1 删**，那 1 行删除是 springdoc `operationId` 自然重排（`GET /boards` 由 `list_2` 变 `list_3`，因四个 Controller 的方法名都叫 `list`），**端点与 schema 语义无变化**；schema 实际 **+7**（§5 估 ~+4，差在 `PageVo<NotificationVo>` 与其 `ApiResponse` 外壳各算一项）。规模：18 → **21 端点**、33 → **40 schema**、tag 7 → **8**、受保护操作 9 → **12**。

**ArchUnit 带来的一处结构性取舍**：G4「跨上下文只允许调用对方 `application`」使 notification **无法复用** forum 的 `PageResult` / `PageVo`，只能在本上下文各自另建一份。**属范式约束下的有意重复**，不是疏忽；若日后要收敛，须先动 §2.4 与守护规则（另开 CR）。

**顺带发现的 1 处未修缺陷（不在本次范围）**：所有时间戳整体偏 **+8 小时**——V1 各表 `created_at DATETIME DEFAULT CURRENT_TIMESTAMP` 写入 MySQL 服务端本地墙钟，而连接串带 `serverTimezone=UTC` 按 UTC 读出。后果按 `utils/time.ts` 分支实算过：`formatRelativeTime` 的 `diff` 恒偏小 8h，**真实 8 小时内的一切一律渲染为"刚刚"**、跨天档位前移约一天（**排序不受影响**，全表等量平移）。已登记为台账外问题 **L-6** 与 **CR-051 候选**，**本次不修、也不在前端做 -8h 补偿**。

**真机取证的两处现实约束**：① `app.roster.bypass` 置 false 后内置名册不可用，双用户场景改由 `/admin/roster/import` 导入额外学籍后注册；② 浏览器工具页面视口 0×0，**无截图、无真实指针点击**，`/notifications` 只做到 DOM 结构 + `getComputedStyle` + `scrollY` 取证——**像素级目视走查仍属未完成**，归口 [W-03](../../流程偏离记录.md) 补偿③（见 [界面规范](../../设计/UI规范/界面规范.md) §8.3）。
