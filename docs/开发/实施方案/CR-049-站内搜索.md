## 1. 目标

落地 PRD [F-FORUM-008](../../需求/产品需求文档.md)：按关键词搜索帖子**标题与标签**，结果按**相关度 + 时间**排序，支持按版块 / 时间窗筛选；空结果有"去提问"引导。验收（PRD）：标题含 "Redis" 的帖子搜 "Redis" 必中，可按版块 / 时间筛选。

## 2. 范围

- **做**：
  - 公开端点 `GET /api/v1/posts/search`：`keyword`（必填，2~50 字）、`boardCode`（可选）、`days`（可选时间窗 7 / 30 / 90 天）、`page` / `size`；出参复用 `PageVo<PostSummaryVo>`；
  - 检索实现：`MATCH(title) AGAINST(...)`（V1 已有 `FULLTEXT ft_posts_title`，ngram 分词，天然支持中文 2 字起）**OR** `posts.tags` 列 LIKE 兜底；排序 `MATCH 得分 DESC, created_at DESC`；只搜 `PUBLISHED` 且未删除；
  - 前端：顶栏搜索框由"只读占位 + toast"改为**可输入**（宽屏输入回车、窄屏图标进入搜索页）；新增 `SearchView`（路由 `/search`），复用帖子列表卡片样式，含版块 / 时间窗筛选与空态"去提问"按钮；
  - 契约快照再生成（v1.8）。
- **不做**：
  - 正文 / 楼层全文检索（属 F-FORUM-009 P1）；
  - `tags` / `post_tags` 关联表启用与**发帖标签输入**——发帖至今未建模标签（`PublishPostCommand` 无 tags、`posts.tags` 全库无数据），搜索命中 tags 列是"有值即生效"的兜底，标签输入本身另行 CR；
  - 搜索热词 / 搜索历史 / 高亮关键词；
  - 外部搜索引擎（ES / MeiliSearch）；
  - 新增 `ResultCode`（keyword 校验失败复用通用参数错误码段）。

### 7.2 与计划的偏差（6 条，均如实登记）

1. **排序补了一个兜底键**：计划写 `MATCH 得分 DESC, created_at DESC`，实际为 `MATCH 得分 DESC, created_at DESC, **id DESC**`——相关度与时间都相同时若不定序，分页会出现同一条帖子跨页重复 / 漏出（MySQL 对等值行不保证稳定顺序）。属计划漏项，实现时补上。
2. **`days` 白名单从"可选筛选"收紧为"只受理 7 / 30 / 90"**：计划只说"可选时间窗"，未定非法值行为。实际按**与 `keyword` 同一口径**处理——非白名单值（如 15 / 0）返回 `400 / 1001`，而不是静默忽略（静默忽略会让用户以为筛了、其实没筛）。
3. **分页参数与关键词的处置口径有意不同**：`page` / `size` 非法值（`page=0`、`size=999`）**静默归一**为 1 / 100，`page=abc` 由框架层类型转换兜住返回 `400 / 1001`；而 `keyword` / `days` 非法一律 `1001` 失败。理由：分页越界是"意图明确、取值出格"，归一不改变用户想看的內容；关键词与时间窗出格则会导致结果集与预期不符，必须显式失败。**这一区分计划里没写，是实现时定的。**
4. **application 层做了一次小重构（计划外）**：把 boardCode → boardId 解析与 `PostSummary` 组装分别提取为 `boardIdOf(...)` / `toSummaries(...)` 私有方法——搜索、列表、"我的收藏"三处的解析与组装逻辑此前是复制粘贴的三份，新增第四处（搜索）前先收口。**未改变任何既有端点的对外行为**（列表 / 详情回归测试全绿）。
5. **单测数比计划多 1 个**：计划估"约 6 例、基线 138 → 约 144"，实际 **+7 → 145 全绿**（`ForumQueryApplicationServiceTest` 6 例：解析与昵称口径 / 1 字 / 空白 / 超 50 字 / `days` 白名单 / 未知版块 3001；`ForumPublicReadTest` 1 例：匿名可读）。
6. **⚠️ 自引入缺陷一处，已在本轮修掉**：`PostController.search` 最初标 `@ErrorCodes({INVALID_PARAM, NOT_FOUND})`，而 `OpenApiErrorResponseCustomizer` 本就会为每个端点**自动补通用 400**，导致快照里 400 的描述重复出现两条。修正为**只声明业务码 `@ErrorCodes({NOT_FOUND})`**——这正是 AGENTS.md「契约声明」约定的原意（通用 400 / 500 不必声明）。**教训**：`@ErrorCodes` 只写业务码，写了通用码就是重复事实。

### 7.4 两处如实标注的边界（非缺陷，是事实）

1. **`keyword` 下限 2 字由引擎决定，不是产品取值**：V1 的 `FULLTEXT ft_posts_title` 用 **ngram 分词**，`ngram_token_size=2`——**单字关键词在引擎侧永远分不出词、恒不命中**。故 2 字下限是把引擎约束显式化为校验，而不是"产品认为 1 字搜索无价值"。若将来要支持单字，须改分词配置或换引擎（属 F-FORUM-009）。
2. **"按标签搜"当前没有真实数据来源**：`posts.tags LIKE` 通道已实现且**经临时数据验证可用**，但**发帖链路从未建模标签**（`PublishPostCommand` 无 `tags` 入参、全库 `posts.tags` 恒为 NULL、`tags` / `post_tags` 两张表未启用）。故 [PRD](../../需求/产品需求文档.md) F-FORUM-008 的"搜索标题**与标签**"目前**只有标题半边有数据**。标签输入属另一个 CR（已在 §2 不做清单）。**正文全文检索 = F-FORUM-009（P1，MeiliSearch）仍未实现。**
