## 1. 目标

让 **[技术方案](../../设计/技术方案.md) §2.5「所有时间字段存 UTC」与 §5「ISO 8601 UTC 传输、展示时区由前端处理」成为事实**，消除 L-6：**全库时间戳整体偏 +8 小时**。

量化验收：新发帖后 DB 中 `created_at` 与 `UTC_TIMESTAMP()` 之差 **< 5 秒**；列表相对时间不再**恒显示"刚刚"**。

## 2. 根因（2026-09-15 真机实测，非推断）

| 环节 | 实测事实 |
|------|---------|
| MySQL 服务器 | 会话 `time_zone = SYSTEM`（本机 +8）：`NOW()=2026-09-15 20:04:24`、`UTC_TIMESTAMP()=12:04:24` |
| 写侧 | `application.yml` 只有 `serverTimezone=UTC`、**无** `forceConnectionTimeZoneToSession` → 驱动不改动会话时区，V1 各表 `DEFAULT CURRENT_TIMESTAMP` 落的是**本地墙钟**（post 15：`2026-09-14 22:38:36`＝当时本地时刻） |
| 读侧 | 字段类型统一为 `java.time.Instant`，驱动按"连接时区 = UTC"解释 DATETIME → 把本地墙钟当成 UTC，**得到晚 8 小时的瞬间** |
| 出口 | API 返回 `"2026-09-14T22:38:36Z"`；前端 `formatRelativeTime` 的 `Date.now()-t` 为**负** → 命中 `diff < 60_000` 分支 → **恒"刚刚"**，`formatTime` 显示 `2026-09-15 06:38` |

**已核实不受影响**：① 列表 / 楼层**排序**（全表等量平移，`ORDER BY created_at DESC` 结果不变）；② 搜索 `days` 时间窗（`PostMapper` 用 SQL `DATE_SUB(NOW(), INTERVAL ? DAY)`，会话内自洽，修复前后都正确）；③ JWT 与验证码（`Instant.now().getEpochSecond()`，不经数据库）。**顺带登记的事实**：`RedisCaptchaStore` 的每日限流键用 `LocalDate.now(ZoneOffset.UTC)`，即**按 UTC 日界计数（北京时间 08:00 重置）**——与本 CR 无关、本次不改。

## 3. 范围

- **做**：
  1. **`application.yml` 一处**：`serverTimezone=UTC` → **`connectionTimeZone=UTC&forceConnectionTimeZoneToSession=true`**（驱动在建连后把会话 `time_zone` 设为 +00:00）→ `CURRENT_TIMESTAMP` 与 `Instant` 绑定**双双落 UTC 墙钟**，"存 UTC"由声明变为事实；驱动为 spring-boot 4.1.1 管理的 **mysql-connector-j 9.7.0**，两参数均支持（`forceConnectionTimeZoneToSession` 自 8.0.23 起提供）；
  2. **存量开发数据：一次性 −8h 校正**（开发库 **11 张业务表 / 19 个 DATETIME 列**全部为本地墙钟（`information_schema` 实测：20 个日期时间列中唯一非 DATETIME 的是 `flyway_schema_history.installed_on`），无一例外）——先 `mysqldump` 全库备份到 `backend/target/`（已 gitignore），再在**同一事务**内对这些列执行 `SET <col> = <col> - INTERVAL 8 HOUR`；**`flyway_schema_history` 排除在外**（其 `installed_on` 是 `TIMESTAMP` 列、由 Flyway 经驱动按连接时区写入，且不参与 `validate-on-migrate` 校验）；**备选路线**为清库重建（`DROP`/`CREATE DATABASE` + Flyway 重跑 V1/V2），本次不采用，理由是重建会丢掉全部夹具、只能验证"新写入"这一半，而校正可同时验证"存量"与"新增"两半；
  3. **配置守护测试**（新增 `config/DataSourceTimezoneTest`）：断言 URL 含 `connectionTimeZone=UTC` 且 `forceConnectionTimeZoneToSession=true`、且不再出现已被弃用的 `serverTimezone=`；
  4. 文档同步：技术方案 §2.5 / §5 加注实测口径、接口契约 README 时间字段口径、台账 §1/§2/§3（L-6 置已处置）/§4、驾驶舱。
- **不做**：
  - **不改 V1 DDL**（已执行迁移不可修改），**不新增 `V*.sql` 迁移**、不把 `DATETIME` 改 `TIMESTAMP`；
  - **不新增 `scripts/data/D*.py` 数据脚本**做 −8h 校正——数据轨硬性约定要求**幂等**，而"按 +8h 写入的历史行"与"已校正行"在取值上无法区分（老数据同样落在过去），该校正**天然不可重入**。生产若已有真实数据，须在维护窗口由人工执行一次性 SQL（见 §7），本 CR 只提供语句、不做成脚本；
  - **不在前端做 −8h 补偿**（掩盖根因、换时区即错）；
  - **不动 `spring.jackson.time-zone: UTC`**——对 `Instant` 序列化无影响（JSR-310 恒输出带 `Z` 的 UTC），改它属噪声；
  - 不改任何 Controller / VO / 错误码 → **契约快照 `git diff` 应为空**（这正是本 CR 的验收点之一）；
  - 不动 `RedisCaptchaStore` 的 UTC 日界计数、不实现热榜（属 Sprint 3 剩余项）。

### 8.2 与方案的偏差（四条）

1. **计划外副作用（此前未发现，如实登记）**：一次性 SQL 按"**一列一条语句**"写，于是同一行的 `updated_at` 被**同批前一条语句隐式顶成校正瞬间**（`ON UPDATE CURRENT_TIMESTAMP` 在它未被显式赋值的那条语句上触发），随后再被它自己那条语句 −8h。净结果：**所有含 `updated_at` 的表，该列现等于校正时刻 `2026-09-15 12:20:51`，原始"最后修改瞬间"丢失**。已实测确认显式赋值本身不会触发 `ON UPDATE`（临时表复现：`ts = ts - INTERVAL 8 HOUR` → 正确得 `04:00:00`），故这是"拆成一列一条"的写法后果，不是 MySQL 语义意外。影响面：**零对外**——`updated_at` 只存在于 `domain/model` 与 `*DO`，8 处引用无一进 VO / 接口（已 grep 核实），纯内部簿记。生产若沿用 §7 语句，应**每表一条语句同时 SET 多个列**以免同样覆盖。
2. **表 / 列计数纠正**：方案初稿写"10 表 / 20 列"，`information_schema` 实测为 **11 张表 / 19 个 DATETIME 列**（第 20 个日期时间列是 `flyway_schema_history.installed_on`，`TIMESTAMP` 类型且不在校正范围内）。已在 §3 / §7 同步为实测值。
3. **验证路线加做了一步（计划外）**：为把 `notifications` 与"采纳他人回复"两条**真实写入口**打到（自触发不发通知、且采纳自己的回复会 `3003` 拒绝），内置测试名册四个学号已被历史夹具占满，故临时以 `APP_ROSTER_BYPASS=false` 重启 → 用 `POST /api/v1/admin/roster/import` 导入一条名册（顺带取到 `audit_logs` 写入口证据）→ 注册出第二账号完成回帖与采纳。**验证结束后已恢复默认 `bypass=true` 并重启**（当前 8088 实例为默认配置）。
4. **前端走查局限新增一条具体成因**：嵌入浏览器 `document.visibilityState = hidden`、视口 0×0、**`requestAnimationFrame` 回调永不触发**，而 [CR-052](./CR-052-前端界面美化.md) 给路由加了 `<transition mode="out-in">` 淡入——离场元素的 `transitionend` 不来，新视图**永不挂载**（`<main>` 文本长度为 0，接口请求已发出且 200）。因此**详情页 DOM 走查在本环境不可执行**，本次改用「API 返回值 + `formatRelativeTime` / `formatTime` 的纯函数换算」取证。这是工具限制、非产品缺陷（真实浏览器恒有 rAF），但它让 [W-03 补偿③](../../流程偏离记录.md) 的"无法目视走查"多了一条可复现的技术解释，**桌面 ≥768 横排仍未目视**。
