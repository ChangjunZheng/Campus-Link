## 1. 目标

兑现 [PRD](../../需求/产品需求文档.md) **F-SAFE-003「内容处置」（P0）中"管理员可对内容下架 / 恢复"这一支**：`PUT /api/v1/admin/posts/{id}/status` 与 `PUT /api/v1/admin/replies/{id}/status` 把 `status` 在 `PUBLISHED ↔ REMOVED` 之间迁移，**处置后前台即时不可见 + 每次处置留审计日志**（PRD 该条验收的前两句），并**首次让生产红线第 4 项「内容处置必须写审计日志」获得真实的调用方**（此前 `audit_logs` 只有 `ROSTER_IMPORT` 与 `POST_DELETE` 两类写入）。

**本 CR 不声称 F-SAFE-003 整项完成**，也不声称 [问题清单](../../项目现有问题清单.md) **F-006** 闭环——F-006 覆盖"举报 / 工单 / 内容下架 / 禁言封禁 / 运营后台"五件事，本轮只碰"内容下架"一支，回置时按**部分**记。第三条验收"作者收到通知"见 §2「不做」第 1 条。

## 2. 范围

**取证先于形状**——四条事实决定了本方案：

- **① 状态是死的**：`PostStatus.java:3` 注释自陈"REMOVED 为内容处置（机审 / 管理员下架）**预留**"，全仓 grep **无任何写 `posts.status` / `replies.status` 的代码**；[问题清单](../../项目现有问题清单.md) 已把"CR-060 的楼层下架分支**当前不可触发**"记为一处缺陷，依据就是同一个事实。本 CR 是这套既有读侧过滤的**生产者**。
- **② 读侧过滤已就位，但有一处不对称**（吸取 [CR-065](../../变更日志/变更台账.md#cr-065) D-1 教训，逐条打开适配器核对，不凭印象）：帖子列表 `findPage`（`PostRepositoryImpl:35`）、搜索（`PostMapper.search` SQL `status='PUBLISHED' AND is_deleted=0`）、热榜候选 `findHotCandidates:129`、`resetHotScoresBefore:159` **四处已过滤 status**；`findById` / `findByIds` **刻意只过滤 `is_deleted`**，status 判定归应用层的 `Post::isVisible`，而详情 / 楼层 / 回帖 / 点赞 / 收藏 / 采纳六条入口都以 `requireVisiblePost` 开头 → **合规**；⚠️ **唯一漏点：通知读时组装** `ForumQueryApplicationService:167` 用 `findByIds` 且**不套 `isVisible`**，下架帖的**真实标题会继续留在别人的通知里**、点进去 404/3001。本轮一并收口（1 行），因为"写侧新增状态、读侧按印象认为各处已一致"正是 CR-065 抓出的缺陷模式。
- **③ 一个反直觉的好消息**：`resetHotScoresBefore` 的条件里已含"非 PUBLISHED"→ **下架即掉出热榜并把分数归零，算分链路零改动**（无须为热榜写任何排除逻辑，也不产生"已下架帖霸榜"的次生缺陷）。
- **④ 处置权归 SUPERADMIN 不是省事，是 PRD 原文**：F-ADMIN-001 写"超级管理员（权限管理 + **处置**）、运营（审核 + 工单处理）"。故复用 `CurrentUser.requireRole(auth, "ROLE_SUPERADMIN")` 的**单值签名**，**不给 `common/web` 加 varargs 重载**（改公共鉴权入口门槛更高，且现无 OPS 账号可测）。

- **做**：
  1. 两个受保护端点 `PUT /api/v1/admin/posts/{id}/status`、`PUT /api/v1/admin/replies/{id}/status`，body `{status: "PUBLISHED"|"REMOVED", reason?: ≤200 字}`；出参 `ApiResponse.ok()`（无 body，同 `accept` / `delete` 先例）；**未登录 401/4001、已登录非 SUPERADMIN 403/4002、目标不存在 404/3001、`status` 取值非法 400/1001**；
  2. **幂等**：目标状态与当前一致 → `200` 且**不记审计**（比照 CR-065"二次删除不重复记 `POST_DELETE`"——同一动作记两条会让审计变噪音）；
  3. 端口新增 `PostRepository#updateStatus(id, target, expectedCurrent)` 与 `ReplyRepository#updateStatus(...)`，**定向单列 UPDATE + 条件带原状态**，返回 boolean（同 `markDeleted` 范式：并发下只有真改到行的一方记审计）；
  4. 新建 `module/forum/application/ContentModerationApplicationService`：读当前态 → 幂等判定 → 改状态 → 审计，**同事务**；审计 action 取 `POST_REMOVE` / `POST_RESTORE` / `REPLY_REMOVE` / `REPLY_RESTORE`，`detail` 记 `reason` 与操作者角色，**不落正文与任何敏感明文**；
  5. 新建 `module/forum/web/AdminModerationController`（`@Tag("admin-moderation")`，照 `AdminRosterController` 结构）；
  6. 修 §2②的漏点：通知摘要补 `.filter(Post::isVisible)`；
  6b. **实施首日读代码新发现、随即并入本批（原方案未列）**：`NotificationApplicationService#toItem` 的 `postId` 取自 `postIdOf(...)` 而**不看 `postBriefs` 是否命中**——于是指向**已删帖 / 已下架帖**的"帖子类"通知仍下发 `postId`，前端 `NotificationsView.vue:68` 的注释写着"原帖已删（服务端不下发 postId）时不给跳转"，**该契约服务端从未真的履行**（只有"楼层类"通知因 `replyBriefs` 查不到而恰好为 null）。条目于是**可点击 → 落 404/3001**，与只做 6 之后"标题回落但链接仍活"叠加，"下架即不可见"就只剩半句。修法 1 行：`postId` 在摘要未命中时置 null（前端已支持、**不改前端**）+ 1 例守护。⚠️ **这条会改到 [CR-065](../../变更日志/变更台账.md#cr-065) 已验证过的通知回落行为**（当时只断言了标题回落、没断言 `postId` 是否下发），故按"先改方案再改代码"在此登记，真机须同时取证**已删帖**与**已下架帖**两种通知条目；
  7. 单测 + 契约快照重生成（+2 operation / 受保护 13 → 15 / schema +1 个请求体）。
- **不做**（每条带理由）：
  1. ⚠️ **不发"作者收到通知"**（PRD F-SAFE-003 验收第三句）。要发通知须给 `NotificationType` 加新值（现仅 reply/like/favorite/accept），而前端 `NotificationsView.vue:63` 是 `if (n.type === …)` **硬编码链**——新 type 在页面上会落到默认分支、文案与语义错位。**`frontend/` 由并发会话占用（[CR-055](../../变更日志/变更台账.md#cr-055) 在途）**。**如实登记后果**：本轮只签"前台即时不可见"与"留审计日志"两句，**第三句不签**，并登记两条前置（通知词表扩展 + 前端文案映射）归后续 CR。
  2. **不做用户警告 / 禁言 / 封禁**：`AccountStatus.BANNED` 同样是零写入口的死状态，登录侧 `USER_BANNED(2006)` 已就位——看似只差一个端点，但 PRD 明写"封禁用户**即时登出**"，而现 JWT 无状态、`JwtAuthenticationFilter` 不查吊销名单，**必须先设计 token 吊销机制**（Redis 名单 / jti / 版本戳三选一），那是独立一轮的架构级变更，不塞进本批。
  3. **不做举报 F-SAFE-002**：`reports` 表 V1 就位、全仓零代码。举报 → 工单 → 处置是**一条链**，本轮先把链尾"处置"接通（有了它，举报才有消费者），下一轮接链头，返工最小。
  4. **不做机审 F-SAFE-001**：依赖第三方选型（设计门 **A3-8 未决策**，决策材料见[部署与机审选型](../../评审/部署与机审选型决策材料.md)）。
  5. **不做处置台 / 工单页 UI**（`frontend/` 占用；且 F-ADMIN-002 验收要求"按关键词 / 用户 / 时间搜索内容"，属查询侧独立一批）。
  6. **不新建 `module/moderation` 上下文**：为两个端点起一套四层不划算，且处置对象是 `forum` 的聚合、状态列在 forum 的表里；A3-11 复评确认的"照抄 account/forum 结构"留给真正的第三个上下文。
  7. **不碰 `is_deleted`、不物理删、不级联**：下架与删除是两件事——作者自助删除走墓碑、平台处置走 status，**列语义一旦合并，事后无法区分"谁删的"**（CR-065 ① 已立此判据，本 CR 是它的第一次兑现）。
  8. **零迁移、零新依赖、零配置项**；不改 `common/web/CurrentUser`、不改 `SecurityConfig` / `EndpointAuthorizationManager`（守护规则 G8 不受影响）。

### 7.1 与计划的偏差（逐条）

| # | 偏差 | 原计划 | 实际 |
|---|------|--------|------|
| D-1 | §3 表里的 `vo/ModerationCommandVo.java` **未建** | 新建 web 层 VO 承载校验 | 本仓惯例是 **web 直接把 `application/cmd/*Command` 当 `@RequestBody`**（`PublishPostCommand` / `AcceptReplyCommand` 先例），另立 VO 会把校验注解抄第二份、必然漂移。改为 `application/cmd/ModerationCommand.java`，**§3 该行按此认定** |
| D-2 | 审计 `detail` **不含操作者角色** | §2「做」第 4 条写了"记 `reason` 与操作者角色" | 唯一可调用者就是 SUPERADMIN，角色写进 detail 是**常量、零信息**；`actor_id` 已能回溯是谁。实际 detail：帖子 `from=… to=… reason=… boardId=… title=…`（标题截 100 字加省略号），楼层 `from=… to=… reason=…`。**楼层侧不记正文与版块**——要读整行才有，处置不值得那个代价（`target_id` + 帖子侧记录可复原现场） |
| D-3 | `status` 用字符串 + `@Pattern` 而非枚举字段 | §3 写"枚举白名单" | 枚举绑定失败会走 `HttpMessageNotReadableException`，提示是"请求体不是合法 JSON"——对"取值不在词表里"是**误导性文案**。改字符串校验后得到 `400 / 1001` 与一句说清可取值的 message（真机第 35 项实测文案 `status 只能取 PUBLISHED 或 REMOVED`）。⚠️ **代价**：词表存了两份（两个枚举 + 一条正则），任一枚举增删都须回头改这条正则，已写进 `ModerationCommand` 注释 |
| D-4 | 单测基线 | §5 估"约 232" | **248**（+28 = 用例层 11 + 适配器 6 + 鉴权 7 + 通知与摘要 4）。估算偏低是因为把控制器鉴权按"三态 3 例"算，实际拆成匿名 / 非超级管理员 / 放行 / 非法 principal / 异常透出共 7 例 |
| D-5 | §2② 的漏点比方案再多一处 | 只补 `postBriefsOf` 的 `.filter(Post::isVisible)` | 补完仍不够——`NotificationApplicationService#toItem` 的 `postId` 只看 `postIdOf(...)`、**不看摘要是否命中**，标题回落了、**链接还是可点**（点进去 404/3001）。即 §2「做」6b 那条，两侧同时收口才兑现"下架即不可见" |
| D-6 | 取证轮次 | 一轮 | **三轮**：① 忘记给 4 个处置调用带 admin token（脚本缺陷，非产品缺陷）；② 回帖用例的 body 写成 `content` 而真实字段是 `contentMd`，于是拿到 `400 / 1001` 而不是预期的 `404 / 3001`——**这是脚本错、不是行为错**，改字段后为 3001；③ 清理函数用**临时表**跨了多条 `mysql` 连接（临时表随连接销毁 ⇒ 清理静默失效），改为单会话多语句。第三轮 45/45 全绿 |

### 7.3 真机取证（临时端口 **8096**、`HOT_REFRESH_INTERVAL_MS=20000`、`VERIFY_IP_HOURLY_LIMIT=300`，**8088 / 8089 与并发会话数据一律未动**）

- **鉴权四态**：匿名 → `401 / 4001`（框架层，未进业务）；作者本人（`ROLE_USER`）→ `403 / 4002`；SUPERADMIN → `200`；非法 `status` → `400 / 1001`；目标不存在 → `404 / 3001`。
- **下架后十二处逐项实测**：全站列表 / 版块列表 / `sort=hot` / 站内搜索 / 详情 / 楼层列表 / 回帖 / 点赞 / 收藏 / 采纳 / "我的收藏" / **通知标题**——前十处不可见或 `404 / 3001`，收藏页不再出现，通知条目回落「内容已删除」**且不再下发 `postId`**（第 31 项，本轮收口的直接证据）。
- **两列两义兑现**：下架后 SQL 实测 `posts.status=REMOVED` 而 `is_deleted=0`（第 11 项）；作者此时调 `DELETE` → `404 / 3001`，**不能借自助删除绕过处置**（第 32 项）。
- **审计**：每次真改动 `audit_logs` +1 行、action 分别为 `POST_REMOVE` / `POST_RESTORE` / `REPLY_REMOVE` / `REPLY_RESTORE`；同状态重复调用 `200` 且**行数不变**（第 33 项）；`reason` 缺省落 `-`（第 34 项）。
- **恢复可逆**：`REMOVED → PUBLISHED` 后四处读侧全部回归、点赞可写、**通知的真实标题也回来了**（第 41~43 项）；楼层恢复后重新出现在楼层列表且**楼层号不变**（第 57 项）。
