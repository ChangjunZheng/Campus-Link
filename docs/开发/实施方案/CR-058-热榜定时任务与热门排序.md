## 1. 目标

兑现 Sprint 3 最后一项、也是 [PRD](../../需求/产品需求文档.md) F-FORUM-003「全站首页"最新 / 热门"双排序」的后端一半：按 [ADR-006](../../设计/技术方案.md) 的公式 `hot_score = 互动分 × exp(-λ × 小时龄)` 定时刷新 `posts.hot_score`，并让 `GET /api/v1/posts` 支持 `sort=latest|hot`。**纯后端**（前端由并发会话占用，本轮零前端改动）。

**为什么现在能做**：`posts.hot_score DOUBLE NOT NULL DEFAULT 0` 与 `KEY idx_posts_hot (hot_score)` 自 V1 就已就位，但代码里**零读零写**（`PostConverter` / `Post` 聚合刻意不建模该列），所以**零迁移**即可落地；同时全仓**没有任何定时任务设施**（无 `@Scheduled` / `@EnableScheduling`，`pom.xml` 无 quartz），本轮是首次引入，故 [技术方案](../../设计/技术方案.md) 的选型决策「`@Scheduled` + Redis 锁」在此落码。

## 2. 范围

**做**：

1. **算分口径（可配，因 [PRD Q6](../../需求/产品需求文档.md) 明确"权重与 λ 待试点数据调优"）**：`互动分 = w_reply×reply_count + w_like×like_count + w_favorite×favorite_count`，`hot_score = 互动分 × exp(-λ × 小时龄)`；默认 **w_reply=3 / w_like=1 / w_favorite=2 / λ=0.05**（λ 取 ADR-006 原文值；回复权重最高——它是论坛的核心互动且成本最高）。小时龄 = `now - created_at`，**负值钳为 0**（防时钟漂移把分数放大）；四项参数落 `campuslink.hot.*`，**改参数不改代码**。
2. **刷新范围有界**：只重算 `status='PUBLISHED' AND is_deleted=0 AND created_at >= now - window-days`（默认 **30 天**）的帖子；**窗口外的 `hot_score` 一次性置 0**——否则老帖会永久保留衰减前的高分，热榜会被"僵尸帖"占据。
3. **执行方式**：`@Scheduled(fixedDelayString)` 默认 **10 分钟**（ADR-006 原文）+ `initialDelay` 15 秒（新部署不必等一个周期才有分数）；跑前先取 **Redis 锁**（`setIfAbsent` + TTL，键走 `RedisKeys.of`），取不到即本轮跳过并记 1 行 DEBUG。**锁是 advisory 而非正确性依赖**：重算是确定性的幂等操作，两实例同时跑结果一致，TTL 到期导致的重复执行无害。
4. **读—算—写回**：分批（默认 500 条/批）读出 `id + 三个计数 + created_at` → 领域策略算分 → **逐条定向 `UPDATE posts SET hot_score=?`**（与既有 `adjustLikeCount` / `updateAcceptedReply` 同范式：**绝不整行回写**，否则会覆盖同事务外并发变化的计数）；**每批一个事务**，不开覆盖整窗的长事务。
5. **`sort` 参数**：`GET /api/v1/posts?sort=latest|hot`，**缺省 `latest` = 与今天完全一致的行为**；`hot` 走 `ORDER BY hot_score DESC, created_at DESC, id DESC`（分数并列时退化到最新序，翻页稳定）；**非法值 → `400 / 1001`**，与同端点族 `days`（只受理 7/30/90）的既有口径一致，**不静默归一**。`sort` 与 `boardCode` 可组合（版块内热榜）。
6. **分层落位**：策略与入参载体落 **domain**（纯 Java、零框架依赖，可单测）；端口方法加在既有 `PostRepository`；用例编排在 **application**；**定时触发器与 Redis 锁落 infrastructure**。

**不做**（逐条给理由，防边界漂移）：

- **前端首页「最新 / 热门」切换**——另一会话正在改前端（`PostDetailView.vue` / `main.ts` / `tokens.css` 等有未提交改动），本轮不碰任何 `frontend/` 文件。**如实登记后果**：本 CR 完成后 F-FORUM-003 的"热门"**只在后端可用**，[PRD §5.1](../../需求/产品需求文档.md) 首页双排序的 UI 一侧仍缺，归入待办由后续 CR（或前端会话空闲后）接入。
- **不新增迁移**（列与索引 V1 已就位）；**不新增复合索引** `(status,is_deleted,hot_score)`——[ER 图与量级预估](../../设计/数据模型ER图与量级预估.md) 的试点量级下 `idx_posts_hot` 足够，登记为**扩容触发点**（热榜查询出现 filesort 或慢查询时再加，届时属结构变更须新增 `V3__`）。
- **不做热榜 Redis 缓存（ZSET）**——直接查 MySQL 走索引；技术方案把"热榜缓存"列为 Redis 用途，但试点量级下加缓存只增加一致性面（缓存与 `hot_score` 双事实源），登记为扩容触发点。
- **不加浏览量 / 点击流加权**——`posts` **无 `view_count` 列**，加列即结构变更；ADR-006 的"被否方案"正是点击流加权，本轮不翻案。
- **不做专门防刷**（PRD Q6 的另一半）——现有基线已含点赞/收藏 toggle 主键去重、通知自触发抑制；专门防刷（同用户高频互动降权等）需要行为数据支撑，试点期无数据，不凭空造策略。
- **出参不暴露 `hotScore`**——无产品需求（前端只消费顺序），暴露即扩大契约面并诱导前端自行排序。
- **不新增管理端"手动刷新"端点**——那会新增一个受保护端点与鉴权面；可测性由"`fixedDelay` / `initialDelay` 可配"满足（验证时临时传短周期）。
- **不动 `CampusLinkApplication.java`**——该文件有并发会话的未提交改动；`@EnableScheduling` 放新建的 `config/SchedulingConfig`。

## 5. 验证

- **单测**（基线 **164** → 预计 **176 ± 3**，全部须绿）：
  - `HotScorePolicyTest`：① 零互动 → 0 分；② λ 生效（同互动分、龄 20h 的分 ≈ 龄 0 的 `e^-1`，用断言容差而非硬编等值）；③ 权重线性可加（reply 权重最高在结果上可辨）；④ `createdAt` 晚于 `now`（时钟漂移）→ 龄钳为 0、不放大；⑤ 大互动分不溢出为 `NaN`/`Infinity`。
  - `HotRankApplicationServiceTest`：① 只对窗口内候选写分；② 窗口外调 `resetHotScoresBefore` 恰一次；③ 候选多于 `batchSize` 时分批（游标推进、不重复不遗漏）；④ **锁未取到 → 一次都不写**（并发实例保护的语义）；⑤ 写回走定向 UPDATE（断言调用 `updateHotScore` 而非 `save`，即不整行回写）。
  - `ForumQueryApplicationServiceTest`：`sort=hot` / `HOT` / 前后空白 → 按热榜查；`sort=foo` / `sort=` 空串 → `1001`；**缺省 → 与改动前同一调用路径**（回归保护）。
  - `ForumPublicReadTest`：匿名 `?sort=hot` → **200**（公开读，不因新参数变受保护）；匿名 `?sort=foo` → **400 / 1001**（参数校验先于任何鉴权语义）。
- **真机**（本机 MySQL / Redis + 后端 8088；**前端不参与**）：
  1. 短周期启动后看到 1 行 INFO 刷新摘要，条数与库内 `PUBLISHED` 帖子数吻合；
  2. SQL 取证：任取一帖手算 `(3×reply + 1×like + 2×favorite) × exp(-0.05×龄h)` 与 `hot_score` 对齐（容差 1e-6，龄按 `UTC_TIMESTAMP()` 与 `created_at` 之差——**CR-051 后两者同为 UTC 墙钟，可直接相减**）；
  3. 造一个可辨场景（给某老帖点赞/回帖把互动分抬上去），验证 `?sort=hot` 顺序变化而 `?sort=latest` 不变；
  4. `?sort=hot&boardCode=tech-qa` 组合、`page/size` 翻页 total 与 latest 一致（同一过滤条件、只换排序）；
  5. Redis 取证：`KEYS campuslink:hot:*` 只见锁键、TTL 合理，**键前缀合规**；
  6. 回归面：`sort` 缺省的列表、搜索（CR-049）、详情、点赞/收藏（CR-048）、采纳（CR-043）、通知（CR-050）各打一次确认无变化；匿名 `POST /api/v1/posts` 仍 **401**。
- **契约**：`openapi.json` **diff 非空且应为纯新增 + 一处 summary 改写**（`GET /api/v1/posts` 的 `sort` 参数）。**端点数与 schema 数应不变**（21 操作 / 19 路径 / 40 schema）——若 schema 数变化说明动到了出参，属越界，须回查。⚠️ 注意 springdoc 的 `operationId` 编号漂移先例（v1.9 的 `list_2 → list_3`）：本轮只加参数不加方法，理论上不触发，但**见删除行必逐行判定**。
- **回归风险自查**：① `findPage` 签名变更是**编译期可见**的（不存在静默漏改）；② 定时任务首次引入 ⇒ 须确认它**不拖慢启动**（`initialDelay` 15s、单线程池、批处理）且**异常不杀死调度**；③ `hot_score` 由恒 0 变为有值 ⇒ 唯一消费者是本轮新增的 `sort=hot`，**既有查询不读该列**，故对现状零影响。

## 6. 回滚

- **代码**：本轮全部为新增文件 + 6 处既有文件的局部改动，`git revert` 单个提交即可完全退出（**无迁移、无不可逆结构变更**）。
- **数据**：`hot_score` 是纯派生列，回滚后一条 `UPDATE posts SET hot_score = 0` 即复原到今天的状态；**不需要备份**（该列此前恒 0，无信息可丢）。
- **开关级退让**：若只想停用定时任务而保留 `sort=hot`（例如刷新出现性能问题），把 `campuslink.hot.refresh-interval-ms` 设为极大值即可——`hot_score` 停止更新后热榜退化为"按最后一次分数排序"，**不会报错、不影响最新序**；若连排序也要退，删 `sort` 参数即可，出参形状从未变过。

### 7.2 实施中被测试抓到的自身缺陷（1 处，已修）

游标分批循环的**第一版把 `batch.size() < batchSize` 的提前退出放在了写回之前**，导致**最后一批不足 `batchSize` 的候选被丢弃、分数永不更新**。`HotRankApplicationServiceTest` 的 3 例当场失败（`expected: 3 but was: 2`；两例的 `updateHotScore` 从未被调用）。修为**先写回该批、再判断是否退出**，`isEmpty()` 守卫仍在最前（故 `batchSize <= 0` 不会死循环）；随之删掉一条因提前退出而永不可达的 Mockito 桩（`eq(3L)`），否则严格桩会报 `UnnecessaryStubbing`。**教训**：计划里"游标推进、不重复不遗漏"这条断言正是为这个缺陷写的，先写测试的顺序救了它。

### 7.3 真机取证（§5「真机」6 项逐条）

- **刷新日志**：短周期（`HOT_REFRESH_INTERVAL_MS=20000`）下连续两轮 INFO「热榜刷新完成：写回 17 条、置零 0 条、耗时 X ms」→ 新增一帖后变 **18 条**，条数与库内 `PUBLISHED AND is_deleted=0` 且在 30 天窗口内的帖子数吻合；线程名 **`cl-sched-1`**（`SchedulingConfig` 的单线程池生效）。
- **算分对齐**：任取一帖按 `(3×reply + 1×like + 2×favorite) × exp(-0.05×龄h)` 手算，与 `hot_score` 的**绝对误差 8.6e-8、相对误差 1.4e-8**（容差 1e-6 内）。⚠️ **取证方法上的一个坑**：首轮对不上（系统性差约一个周期）是因为**比对期间又跑了一轮刷新**，故改为从"日志时间 − 耗时"反推**该轮的算分时刻**再比，误差即降到 1e-8 量级；零互动帖全部为 **0**。
- **排序差**：给老帖加点赞 / 回帖抬高互动分后，`?sort=hot` 顺序**可见变化**（目标帖由 #4 升至 #2），`?sort=latest` **完全不变**；`sort` 缺省与 `sort=latest` 结果一致（回归保护）。
- **组合与分页**：`?sort=hot&boardCode=tech-qa` 正常；`page`/`size` 翻页的 `total` 与 `latest` 一致（同一过滤条件、只换排序）。
- **非法值**：`?sort=foo`、`?sort=newest` → **400 / 1001**；未知 `boardCode` → **404 / 3001**。
- **Redis**：`KEYS campuslink:*` 下只见 **`campuslink:hot:refresh:lock`** 一个热榜键，前缀合规、**无裸键**；TTL 合理。锁的**抑制效果已实测**：手工占住该键后 45 秒窗口内**零刷新**（只 1 行 DEBUG），键过期后自动恢复。
- **默认配置复跑**：`initialDelay` 实测 ≈15.5 秒、锁 TTL 读数 298/300、40 秒窗口内**恰好一次**刷新、`/actuator/health` 200 —— 10 分钟周期不影响正常使用。
- **回归面**：`sort` 缺省列表、搜索（CR-049）、详情、点赞 / 收藏（CR-048）、采纳（CR-043）、通知（CR-050）各打一次均无变化；匿名 `POST /api/v1/posts` 仍 **401**；`hot_score` 由恒 0 变有值**未影响任何既有查询**（既有查询不读该列）。
- ⚠️ **一次异常与判定**：某轮启动日志出现 `Started in 1806.569 seconds`，**非调度开销**——同代码同配置的首次启动为 **6.097 秒**；该次 Hikari 打出 `Thread starvation or clock leap detected (housekeeper delta=30m18s)`，且 CaptchaService 的 WARN 与 MyBatis `TableInfoHelper` 之间有单个 **1789 秒**空档，判定为**机器级停顿**（休眠 / 时钟跳变），与 CR-058 无关。
