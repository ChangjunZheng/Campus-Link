## 1. 目标

把 [BUG-003](../../项目现有问题清单.md) 从「漏配环境变量 → 应用照常启动、只是打一行 WARN」改成**启动即失败**：以 `prod` profile 启动时，任何一条生产红线处于开发态（旁路开着、验证码固定、密钥仍是仓库里的开发字面量、口令仍是 `campuslink/campuslink`、验证码只写日志）都必须让进程起不来。量化口径：**四条可机器化的红线全部由代码强制**，`mvn verify` 基线 192 → 约 201。

## 2. 范围

- **做**：
  1. 新增 `backend/src/main/resources/application-prod.yml`（本仓**第一个** profile 文件——现全仓 `@Profile` / `Environment` 判定**零处**，`application.yml` 里 `${VAR:dev-default}` 的默认值就是唯一生效值）：开发开关**显式关掉**（`roster.bypass=false`、`captcha.fixed-code=` 空、`code-sender.mode=mail`），三把密钥与库口令写成**无默认值**的 `${JWT_SECRET}` 形式（占位符解析不出来即启动失败，这是第一道防线）。
  2. 新增 `config/ProductionSafetyGuard`（`@Profile("prod")`）：一次性校验下列各项，**收集全部违规后一起抛** `IllegalStateException`（让运维一轮改完，而不是逐个试错）；通过则打 1 行 INFO，**只记各项的字节长度与 SHA-256 前 8 位指纹，绝不落密钥明文**。
  3. 校验项（6 条）：JWT secret / hash key / crypt key 各自 ① 不等于 `application.yml` 里的开发字面量 ② ≥32 字节 ③ hash 与 crypt 不得相同；固定验证码必须为空；`roster.bypass=false`；`code-sender.mode=mail`；`spring.datasource` 用户名与口令不得同时为 `campuslink/campuslink`。
  4. 新增 `ProductionSafetyGuardTest`（沿用 `DataSourceTimezoneTest` 的 `YamlPropertiesFactoryBean` + `ClassPathResource` 范式）：6 条违规各 1 例、全合规 1 例、多违规同时命中时消息**逐条点名** 1 例，外加两条**防漂移**用例——(a) guard 内的开发字面量清单必须与 `application.yml` 的占位符默认值逐一相等；(b) `application-prod.yml` 的三处密钥声明必须仍**不含** `:default` 段。
- **不做**（逐条理由，防边界漂移）：
  - 不写部署脚本 / Docker 编排 / 环境变量清单交付——**A3-8 部署与机审选型尚未决策**，本 CR 只交付"配置分层 + 启动校验"，不替发起人决定部署形态。
  - 不用 `@ConfigurationProperties` + JSR-380 `@Validated` 注解实现校验——校验语义是**跨字段比对 + 与已知开发字面量比对**，不是单字段格式；注解会把规则摊平进属性类，反而不可读、且无法产出"一次列全违规"的消息。
  - 不校验 CORS 白名单、审计日志覆盖面、机审 fail-closed 开关——后两者对应的功能（F-SAFE-001 / F-SAFE-003、处置台）尚未实现，**无配置项可校验**；CORS 不在 BUG-003 清单内，登记为后续项。
  - 不改开发期默认行为（本机仍零配置可起、验证码仍 `123456`），不改 `CaptchaService` 那条既有 WARN（dev 仍需要它提醒）。
  - 不改 `InMemoryTestRosterGateway` / `DevAdminAccountSeeder` / `LogCodeSender` 三处 `@ConditionalOnProperty(matchIfMissing = true)` 的装配条件——见 §7 已知残余，改它会影响默认 profile 的装配、扩大回归面。
  - 不新增自检端点（属接口契约变更，须另开 CR）、不重生成 `openapi.json`（本 CR **零接口改动**，快照 `git diff` 应为空）。

## 7. 已知残余与诚实边界（写给评审，不粉饰）

1. **`matchIfMissing = true` 是 fail-open 的**：`InMemoryTestRosterGateway`、`DevAdminAccountSeeder`、`LogCodeSender` 三处在"属性整体缺失"时选中的都是**开发实现**。本 CR 靠 `application-prod.yml` 显式赋值绕过，并**由守卫断言 `bypass=false`**，但真正的修法是 `matchIfMissing=false` + 由 dev 配置显式打开——那会改动默认 profile 的装配路径，本批刻意不做。
2. **本仓无 Spring 上下文级测试**（问题清单 E-001）：新守卫的用例是"构造入参 → 断言抛出"的纯单测 + 真机启动各一轮，**不能据此声称 Spring 装配与 profile 切换已被机器覆盖**。
3. 若 `prod` profile 文件被误删而只留 `SPRING_PROFILES_ACTIVE=prod`，Spring 会静默按默认配置启动——**这一条不在本 CR 的拦截面内**（profile 文件缺失是打包期问题），如实登记。
4. **落地 ≠ 验收**：本 CR 关闭的是"漏配能否启动"，不关闭 A3-8（部署与机审选型）、不关闭提测准入门任何一项，`W-*` 一律不动、**不代签**。

**落码偏差与方案被实测推翻处（如实记）**：

1. **守卫的装配形态与方案不同：`InitializingBean` → `BeanFactoryPostProcessor`**。方案未指定生命周期钩子，首版按 `InitializingBean` 落地后，**真机三轮一次都没让守卫说话**（三轮输出里 grep「生产安全配置」均 0 命中）：普通 bean 的初始化排在数据源、Flyway、`JwtService` 之后，prod 漏配时先炸的是 `WeakKeyException: … 104 bits`（A 轮）和 `Access denied for user '${DB_USER}'`（B 轮）。改为 BFPP（在常规 bean 之前实例化）+ `EnvironmentAware` 后，A / B 轮的**第一条**异常即守卫消息。**这条是本轮最实质的收获：没有真机三轮，方案会以为已经成功了。**
2. **方案 §2 做①"占位符解析不出来即启动失败，这是第一道防线"不成立**，已按实测改写。两条读取路径口径不一致：`env.getProperty(key)` **严格**解析，解析不了抛 `PlaceholderResolutionException`；而 Boot 绑定 `@ConfigurationProperties`（数据源走这条）**非严格**，解析不了把 `${DB_USER}` **字面量原样注入**——B 轮 MySQL 报出的用户名就是那七个字符。所以"不留默认值"既不中止启动、也不是零代码防线。守卫据此新增一类违规「未注入：占位符无法解析」，并在 `value()` 里捕获异常，否则第一条未解析占位符就会**吞掉其余全部违规**、把"一次列全"打回"一次一条"。`application-prod.yml` 的原注释同步改正。
3. **A 轮暴露一处自伤误报并已修**：两把密钥都未注入时，两个内部哨兵值相等，被 `checkDistinctKeys` 报成「APP_HASH_KEY 与 APP_CRYPT_KEY 相同」——让人去查一个不存在的问题。改为**只在两个真实取到过的值之间比较**，并补一条回归用例（`unresolvedKeysAreNotReportedAsIdentical`）。A 轮违规数因此由 5 收敛为 4。
4. **prod 三个开发开关写成字面量而非 `${VAR:false}`**：方案只说"显式关掉"，实现选择把 `fixed-code` / `bypass` / `mode` **写死**为 `""` / `false` / `mail`，为的是消灭"部署脚本没带变量就回退到开发值"这条路径。⚠️ 但**字面量不消灭覆盖本身**——`CAMPUSLINK_CAPTCHA_FIXED_CODE=123456` 这类环境变量或 `--campuslink.roster.bypass=true` 命令行参数照样盖得过 yml（Spring Boot 属性源优先级），所以这三条红线的**真正兜底是守卫断言，不是 yml 写法**；本条与 `application-prod.yml` 内注释均已按这个口径写清。由 `prodFileKeepsFailClosedShape` 用例锁死 yml 形状（见反证 6）。
5. `application.yml` 实际只新增 **5 行注释**（`git diff --numstat` = `5 0`），**没有任何取值改动**，与 §2 不做④"不改开发期默认行为"一致；防漂移用例读的是原文，故注释不影响判定。

**§7 四条残余的当前状态**：① 未做（三处 `matchIfMissing = true` 原样保留，本 CR 靠 prod 显式赋值 + 守卫断言绕过）；② 未做（本仓仍无上下文级测试，"prod 真的会拦"只有真机取证支撑，**不得读成装配已被机器覆盖**）；③ 未拦（`application-prod.yml` 被误删时 Spring 静默按默认配置启动，属打包期问题）；④ 依旧成立——本 CR 只关"漏配能否启动"，A3-8 与提测准入门一项未动。
