## 1. 目标

让「楼层写用例」只能作用在**可见的回复**上：`status='REMOVED'` 或 `is_deleted=1` 的楼层，点赞与采纳一律 `404 / 3001`，消除"前台看不到、仍可操作"的读写口径不一致。

## 2. 范围

**做**

- `ReplyRepository` 读侧新增 `findVisibleById`（SQL 侧同时过滤 `status='PUBLISHED'` 与 `is_deleted=0`），并**删除 `findById`**——取证：`findById` 全仓**只有两个调用方**（`InteractionApplicationService:51`、`PostApplicationService:60`），正是本条点名的两条写用例，整体替换后旧方法零调用方，不留"两种读法"并存（并存即未来有人挑错那个）。
- `InteractionApplicationService.toggleReplyLike`（楼层点赞）与 `PostApplicationService.acceptReply`（采纳最佳答案）改用 `findVisibleById`，**错误码与响应形状不变**（仍 `PostNotFoundException` → `404 / 3001`，沿用"不可读统一 404、不区分原因"的防枚举口径）。

**不做（逐条带理由）**

- **不给 `Reply` 聚合加 `status` 字段 / `ReplyStatus` 枚举**（照 `Post` 范式对称化）：`Reply` 今天没有任何业务规则消费 status，加了要改 `rehydrate` 签名、`ReplyConverter` 与全部楼层测试的构造调用，为对称扩大改动面；`ReplyRepositoryImpl:23` 的既有注释也已声明"本 Sprint 不建 `ReplyStatus` 枚举，过滤条件下推至 SQL"。
- **不动 `findByIds`**（通知读时组装用）：引用一条已下架楼层的"第几楼"仍应显示，过滤它会让通知渲染成 `#undefined`——`CR-050` 真机踩过同类缺陷。
- **不给 `adjustLikeCount` 加 status 条件**：守卫只放读侧一处，两处表达即两个事实源。⚠️ 已知残余：读→写之间的 TOCTOU（读时可见、写前被下架）不堵，当前无写 status 的入口，且与 `CR-058` 逐条 UPDATE 的并发口径同类。
- **不处理"已采纳楼层后来被下架"**（`posts.accepted_reply_id` 指向不可见楼层）：等机审 / 处置台（F-SAFE-001/002/003）落地时随其一起设计可见性规则。
- **不改前端、不新增迁移、不改 OpenAPI**（见 §5）。

⚠️ **一条必须知道的定性**：本缺陷**当前不可触发**——全仓无任何写 `replies.status` 的代码（`ReplyConverter` 不写该列，DB 默认 `'PUBLISHED'`），`REMOVED` 只能由人工改库产生。本 CR 是**处置台落地前的前置防线**，不是修一个正在发生的漏洞；因此严重性登记为"中"（与问题清单 §3.1 归类一致，如实说明：清单把它列在高优先级下，但按可触发性应属中）。

## 7. 实施结果（2026-09-18，本方案按发起人批复实施完毕）

**结论：已落地并验证通过。** 三层各改一处 + 一个新适配器测试类 + 两份应用测试改造，**单测 187 → 192 全绿**、**真机取证 17/17 通过**、**契约快照零 diff**。

|---|---|

**落码偏差（如实记）**：

1. **步骤 1 的红绿顺序未按方案执行**。方案要求"先写测试、让它先红在缺 `status` 条件上"，实际是**实现与测试同批写完**，再用**反证实验**替代"先红"：临时注释掉适配器里的 `.eq(ReplyDO::getStatus, STATUS_PUBLISHED)` → 跑测试。两次实验（见下条）证明守卫确由机器强制，效果与红绿顺序等价，但顺序与方案不同，登记为偏差。
2. **首轮反证只红 1 例，暴露出我自己写的用例名不符实**。`writeSideFilterMatchesListFilter`（"与列表同源"）原本**只断言了列表侧**条件，写侧丢失 `status` 过滤它照样通过——即"同源"从未被真正比对。已改为**逐列比对两侧绑定值 + 各自断言列条件只出现一次**，二次反证 **2 例同时红**（`visibleQueryCarriesBothConditions` 与 `writeSideFilterMatchesListFilter`），随后复原守卫、全量 192 绿。教训：**断言"同源"必须两侧都比**，只比一侧等于没比。
3. **真机取证未改动既有数据，改为自建取证帖**。方案写"把某条楼层置 `REMOVED`"，实际**新发帖 1 篇 + 楼层 2 条**（楼主 `模拟学生01` / 楼层作者 `模拟学生02`），只把自己新建的那条楼层置 `REMOVED`，避免在并发会话在用的共享库上改动他人数据。取证后置 `is_deleted=1` 并清掉本次衍生行。
4. **首轮真机有 1 项 FAIL，根因在取证脚本而非产品**。脚本复位时只清了 `posts.accepted_reply_id`，漏了 `posts.is_accepted` 这一**独立列**（详情响应的 `accepted` 由它映射），于是"帖子详情仍可读"断言读到 `accepted=true` 而失败。补齐复位列名后 **17/17 全过**。顺带确认一件事后才写进用例：`accepted` 在 `posts` 表**没有对应列名**，列名是 `is_accepted`。
5. **环境**：本机 Redis 未在跑（6379 无监听），按 `AGENTS.md` 路径先起 Redis；后端起在**临时端口 8096**（8088 / 8089 未动），取证与快照抓取完成后已终止该实例（Redis 保留运行）。

**取证证据摘要**（临时实例 8096，`APP_ROSTER_BYPASS=false`、固定验证码 `123456`）：

- 正常态正向对照先过：可见楼层点赞 200 / 采纳 200——保证后面的 3001 不是"端点坏了"；
- 楼层置 `REMOVED` 后：点赞 `404 / 3001 资源不存在`、采纳 `404 / 3001`；
- 零副作用逐项取零：`replies.like_count` 0→0、`likes` 关系行 0→0、`posts.accepted_reply_id` 仍 NULL、`posts.is_accepted` 仍 0、`replies.is_accepted` 仍 0、发给楼层作者的通知 0→0；
- 读写口径同源：`GET /posts/{pid}/replies` 列表只剩对照楼层（下架楼层不出现），帖子详情 `code=0`、`replyCount=2` 未被误伤；
- 复原 `status='PUBLISHED'` 后：同一条楼层**仍可正常点赞与采纳**（修复未误伤可见楼层），`accepted_reply_id` 正确写入；
- 鉴权层无回归：匿名点赞楼层 `401 / 4001`。
