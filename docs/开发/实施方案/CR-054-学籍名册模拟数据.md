## 1. 目标

发起人指示："学籍名册先改为往数据库添加学生信息，后续再进行优化"——用 Python 脚本模拟 45 名学生进 MySQL，并把账号写进 `docs/` 下的文档。**摆脱 B1/B2 真实名册这一唯一外部依赖**，让注册链路在 `bypass=false`（真查库）下可被验证、后续功能有真实量级的账号可用。

量化口径：`student_roster` 中 `source_batch='dev-sim-45'` **45 行**、`used_user_id` 非空 **45 行**、`users` 新增 **45 个 USER 账号**、这 45 个账号**能用文档里写的登录方式真的登进去**。

## 2. 范围

- **做**：
  - 名册入库走既有 **`POST /api/v1/admin/roster/import`**（SUPERADMIN，CSV `学号,姓名[,年级[,专业]]`）——该路径**自带审计日志**（生产红线要求）、`saveIfAbsent` 天然幂等、且**不受 bypass 影响**始终写库；HMAC 由 `CryptoService` 算，**脚本不碰 `APP_HASH_KEY`**；
  - 账号入库走三个公开端点的真实链路 `verify-student → captcha → register`：`users.email_enc / student_id_enc / *_hash` 与名册占用全部由**生产代码**产生，脚本不复刻 AES-GCM；
  - 学号取**保留段 `888800001`~`888800045`**（真实名册不可能出现的 9 位号段），姓名 45 个合成中文名（2~16 汉字），邮箱 `dev-stu-01@dev.campuslink.local` …（域名为不存在的保留域，收不到真邮件），昵称 2~32 自由文本；批次标记 `dev-sim-45`，年级/专业填「模拟」；
  - 新增 **`docs/开发/开发测试账号清单.md`**（45 行：学号 / 姓名 / 登录邮箱 / 昵称 + 登录口径），并在 [`docs/README.md`](../../README.md) §2、[`AGENTS.md`](../../../AGENTS.md)「常用命令」挂指针。
- **不做**（防边界漂移）：
  - **不引入"密码"概念**。已实测：全库无 `password` 列、`src/main/java` 零引用；登录 = **邮箱 + 验证码**（dev 固定 `123456`，见 AGENTS.md）。所以清单交付的是"账号 + 登录方式"，**标题与表格都不写"密码"**。要真密码登录属需求变更（PRD F-ACC-001），另开 CR；
  - 不改 `app.roster.bypass` 的默认值（仍 `${APP_ROSTER_BYPASS:true}`）、不删内置测试名册的 4 条；
  - 不加 Flyway 迁移（无结构变更）、不改 `V1` DDL、不在名册表加明文学号列；
  - 不导入任何真实学生姓名/学号，不改 B1/B2 正式导入方案；
  - 不让这 45 个账号产生帖子/评论/通知（内容量级另议）。

## 5. 验证

- **单测**：不新增用例（无 Java 逻辑改动），基线 **164 必须仍全绿**；
- **SQL**：`SELECT COUNT(*), SUM(used_user_id IS NOT NULL) FROM student_roster WHERE source_batch='dev-sim-45'` → `45 / 45`；`SELECT student_id_hash FROM student_roster WHERE source_batch='dev-sim-45' LIMIT 1` 为 64 位小写十六进制；`DESCRIBE student_roster` 确认**没有**新增明文学号列；
- **真机**：① bypass=false 下一个**尚未注册**的模拟学号能过 `verify-student`（证明查的是库、不是内置名册）；② 已注册的学号再核验 → 一律 `2101`（三种失败同提示的**防枚举口径未被削弱**）；③ 清单里任取 3 个登录成功；④ 名册导入在 `audit_log` 留有记录（红线"名册导入必须写审计日志"由 API 路径自然满足）；
- **契约**：`openapi.json` 零 diff（不动 Controller / `ResultCode` / 外壳）；
- **回归面**：默认启动（不传环境变量）时 bypass 仍 true、内置 4 条测试名册仍可用、`/actuator/health` UP、`verify` 限流仍 10/小时。

## 6. 回滚

- **无结构变更** → 不涉及 Flyway 回滚；`application.yml` 单行 revert 即恢复；
- **数据回退**（两条语句，顺序敏感）：先按清单里的 45 个邮箱定位并删除 `users` 及其行生数据，再 `DELETE FROM student_roster WHERE source_batch='dev-sim-45';`。开发期更省事的办法：用步骤 4 的 `mysqldump` 备份恢复整库；
- **不可逆点**：这 45 个学号一旦注册即被占用，重复核验必然 `2101`——要恢复"可注册"状态必须删掉对应 `users` 行并置空 `used_user_id`；除此之外只影响本机 dev 库，无外部副作用；
- `VERIFY_IP_HOURLY_LIMIT` 是启动期环境变量，不传即回 10，**不留下任何放宽过的默认配置**。

## 7. 实施结果（实施后追加，不回改上文）

**结论：已实施，§1 的四项量化口径全部达成**（名册 45 行 / 占用 45 行 / 账号 45 个 / 清单里的登录方式实测可用）。执行时间 2026-09-15 22:21~22:40，两次 `--apply`（首灌 + 幂等复核）。

### 7.1 与计划的偏差（3 处）

**偏差①（步骤 4/5 合并为单实例一次跑完）**：计划是"先 bypass=true 起栈灌名册 → 再重启 bypass=false 灌账号"，理由是 admin 由 `DevAdminAccountSeeder`（`@ConditionalOnProperty(bypass=true)`）创建、顺序不可倒。**实际不需要两次重启**：dev 库里 admin 行**早已存在**（此前会话已种子化），故一个 `APP_ROSTER_BYPASS=false` 的实例即可同时完成名册导入与账号注册，`--stage=all` 一次跑完。

进一步偏差：**没有重启发起人在跑的 8088 实例，而是另起 8089 并存**——终止 8088 两次被拦（`taskkill //PID` 被工具判为 UNC 路径；`Stop-Process` 与 `taskkill /PID /F` 均被 Auto 模式分类器判为"终止进程需用户确认"）。改用 `SERVER_PORT=8089 APP_ROSTER_BYPASS=false VERIFY_IP_HOURLY_LIMIT=60` 起第二实例、脚本用 `API_BASE` 指过去，**不动发起人的进程**。两实例共享同一 MySQL / Redis，数据落点与计划完全一致。

**偏差②（步骤 6 的浏览器目视走查未完成，改走 API 层实证）**：内置浏览器 `document.visibilityState=hidden`，Vue 路由 `<Transition mode="out-in">` 的**离场过渡永不结束**（DOM 停在 `route-fade-leave-active` 空壳），登录表单渲染不出来；派发合成 `transitionend` 亦无效，重载同样卡住。**如实登记：浏览器目视未做**。替代证据是脚本内登录复核 **3/3 通过**——`POST /auth/captcha` → `POST /auth/login`（200 / `code=0`）→ `GET /users/me`（200 且 `nickname` 与清单逐字相符），走的是同一后端、同一库、同一 JWT 链路。本 CR **无任何前端改动**，该限制与 [CR-052](CR-052-前端界面美化.md) 遗留的桌面走查同属一类环境问题，归口 W-03 补偿③ / A3-6，不在本 CR 内解决。

**偏差③（计划外多改一个文件）**：[`backend/scripts/README.md`](../../../backend/scripts/README.md) 除登记「执行记录」外，还修正了**建档期留下的编号冲突**——其命名规范与执行示例用的假想名 `D001__backfill_user_grade.py` 与本次真实占用的 `D001` 撞号（序号不可复用），已把示例改为 `D0xx__…（假想示例，勿真建）` 并注明 D001 归属；同时补一条说明：D001 **对库只读、写入靠编排 HTTP 接口**，与 `_template.py` 的纯 SQL 路子不同，后续脚本不要模仿。

### 7.2 实施中发现并自修复的脚本缺陷（1 处）

首灌那轮登录复核 **0/3 失败**（`400 / 2005 邮箱或验证码错误`）。根因不在数据、在脚本：`campuslink.captcha.resend-interval-seconds=60`，注册阶段刚消耗掉验证码，登录复核立刻重发被 `2002` 拒，而原脚本把 `2002` 当"可继续"，于是拿一个**已不存在**的码去登录 ⇒ 必然 `2005`——**把环境时序误报成"账号不可用"**。已改为：遇 `2002` 等待 `CAPTCHA_RESEND_WAIT`（默认 61s，可用环境变量覆盖）后重发一次，重发仍不成功才跳过该账号。修后重跑 **3/3 通过**。

### 7.3 新发现的共享态副作用（计划未预见，已复位）

`verify` 的 IP 限流键 `campuslink:verify:ip:<ip>` 存在 Redis 里，**两个后端实例共用同一个键**。我在 8089 上跑的 45+ 次核验把计数抬到 47，导致发起人的 **8088 实例（默认 10 次/小时）当场对学籍核验返回 `429`**——实测复现并取证。已 `DEL` 该键复位（真实键名为 IPv6 映射形式 `campuslink:verify:ip:0:0:0:0:0:0:0:1`），复测 8088 内置名册核验恢复 `200 / code=0`，`--scan` 确认无残留。

**纪律（写入清单文档）**：批量灌数据后必须清这个键，否则同机默认实例会被连带限流最长 1 小时。
