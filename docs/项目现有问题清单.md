## 3. 已确认的代码 Bug 与技术风险

### 3.1 高优先级

#### BUG-001：楼层点赞存在跨帖子操作风险（已修复）

**状态：✅ 已由 CR-059 于 2026-09-17 修复。**

- 原问题：`ReplyController.like` 接收了路径参数 `postId`，但调用 `toggleReplyLike` 时没有传递或校验它。
- 原问题：application 层只按 `replyId` 查询回复，允许跨帖子拼接路径执行点赞。
- 修复结果：现在先校验父帖可见，再校验回复 `postId` 与路径 `postId` 匹配；不匹配统一返回 `NOT_FOUND / 3001`，不触发点赞、计数或通知。

证据：`ReplyController.java:77-81`、`InteractionApplicationService.java:48-57`、CR-059 实施方案。

验证结果：

1. 同帖点赞正常；
2. 跨帖子回复返回 3001，且不触发 toggle / 计数 / 通知；
3. 父帖不可见返回 3001，且不查询回复；
4. `mvn verify` 187/187 全绿。

#### BUG-002：已下架回复仍可能被点赞或采纳（已修复）

**状态：✅ 已由 CR-060 于 2026-09-18 修复。**

- 原问题：`ReplyRepositoryImpl.findById` 只过滤 `is_deleted=false`，没有过滤 `status='PUBLISHED'`。而以下两个写用例直接使用它：
  - `InteractionApplicationService.toggleReplyLike`：可操作状态为 `REMOVED` 的回复；
  - `PostApplicationService.acceptReply`：可能把状态为 `REMOVED` 的回复作为最佳答案。
- 原问题：列表查询虽然过滤了 `status='PUBLISHED'`，但写操作的可见性口径没有复用，形成“前台看不到、仍可操作”的不一致。

**修复结果**：读侧方法整体替换为 `findVisibleById`（**删除** `findById`——取证它全仓恰有这两个调用方，替换后零调用方，不留两种读法并存），SQL 侧同时过滤 `status='PUBLISHED' AND is_deleted=0`，与列表方法 `findPageByPostId` 同源；两条写用例改用它核验目标，不可见一律 `404 / 3001`（沿用不区分原因的防枚举口径）。守卫**只放在读侧一处**，`adjustLikeCount` 不重复表达同一条件（两处即两个事实源；读→写之间的 TOCTOU 登记为已知残余）。

**严重性定性（方案阶段取证，与清单原归类不同）**：⚠️ 该缺陷**当前不可触发**——全仓无任何写 `replies.status` 的代码（机审 F-SAFE-001 / 处置台 F-SAFE-003 未实现，`ReplyConverter` 不写该列、由 DB 默认 `'PUBLISHED'`），`REMOVED` 只能人工改库产生。故本条实为**处置台落地前的前置防线**，严重性据实由 §3.1 的“高优先级”**下调为中**（保留在本节、只加注，不重排历史条目）。

证据：`ReplyRepository.java`（`findVisibleById` javadoc）、`ReplyRepositoryImpl.java`、`InteractionApplicationService.java`、`PostApplicationService.java`、CR-060 实施方案 §7。

验证结果：

1. 单测 **187 → 192** 全绿（新增 `ReplyRepositoryImplVisibleTest` 3 例 + 应用层 2 例零副作用断言）；
2. 反证实验（临时摘掉 `status` 条件）：`visibleQueryCarriesBothConditions` 与 `writeSideFilterMatchesListFilter` **两例同时失败**，复原后全绿——守卫确由机器强制；
3. 真机取证 **17/17**：置 `REMOVED` 的楼层点赞 / 采纳均 `404 / 3001`，`replies.like_count`、`likes` 关系行、`posts.accepted_reply_id`、`posts.is_accepted`、`replies.is_accepted`、楼层作者通知**全部零变化**；列表不再出现该楼层（读写同源实测成立）、帖子详情未误伤；复原 `PUBLISHED` 后同一条楼层仍可点赞与采纳，匿名点赞仍 `401 / 4001`；

#### BUG-003：生产环境默认配置不安全（已修复）

**状态：✅ 已由 [CR-063](变更日志/变更台账.md#cr-063) 于 2026-09-18 修复并验证。** 下面的原描述与那条 09-18 注**一字未改**，只在文末追加实施结果。

`application.yml` 在没有环境变量覆盖时会启用：

- JWT 默认签名密钥；
- AES / HMAC 默认密钥；
- 固定验证码 `123456`；
- 学籍核验旁路 `bypass=true`；
- 本地数据库默认账号密码。

当前代码只打印 WARN，没有阻止应用以这些配置启动。只要部署环境漏配变量，系统可能在“看起来启动成功”的状态下运行在弱安全模式。

证据：`backend/src/main/resources/application.yml:67-94`。

建议修复：按 profile 分离开发与生产配置；生产 profile 启动时强制校验密钥、`bypass=false`、固定验证码为空、`CODE_SENDER_MODE=mail`，不满足即启动失败。

### 3.2 中优先级

#### BUG-004：前端没有处理 token 过期后的统一退出

Pinia 只根据 `localStorage` 中是否存在 `cl_token` 判断登录态，没有保存或检查 `expiresAtEpochSecond`；路由守卫因此会把已过期 token 当成登录状态。后续接口返回 401 时，`client.ts` 只抛出 `ApiError`，没有清理会话、跳转登录或保留回跳地址。

表现：用户打开已过期的浏览器页面时可以进入受保护路由，页面随后显示接口错误，而不是统一回到登录页。

证据：`frontend/src/stores/auth.ts`、`frontend/src/router/index.ts:20-31`、`frontend/src/api/client.ts`。

#### BUG-005：正文长度实现与 PRD 不一致

PRD F-FORUM-002 定义正文上限为 20,000 字，但后端 `PublishPostCommand` 和 `PublishReplyCommand` 均允许 50,000 字，前端 textarea 也允许 50,000 字。

这不是单纯文案问题：接口验收、数据库容量估算、机审耗时和性能指标都会受影响。

证据：PRD F-FORUM-002、`PublishPostCommand.java:7-10`、`PublishView.vue`。

建议：产品确认统一为 20,000 或更新 PRD / 测试 / 性能预算，不能长期两套口径并存。

#### BUG-006：内容安全文案与实际行为不一致

发帖页明确展示“发布前将进行内容安全机审”，但当前发帖 / 回帖服务没有机审调用。该问题会导致用户对平台安全能力产生错误预期，也容易在验收时被误判为已完成。

证据：`PublishView.vue`、`PostApplicationService.java`、`ReplyApplicationService.java`。

#### BUG-007：热榜锁配置存在静默降频风险

配置注释要求锁 TTL 不应大于刷新周期，但代码没有启动校验。若锁 TTL 大于刷新周期，上一轮锁未过期时下一轮会直接跳过，实际刷新周期可能变成 TTL，且不会报错。

证据：`application.yml:95-105`、`AppProperties.Hot`、`HotScoreRefreshScheduler`。

建议：增加配置校验，约束 TTL、刷新周期、窗口天数和批大小的合法范围。

#### BUG-008：互动计数使用字符串拼接 SQL

`adjustLikeCount`、`adjustFavoriteCount` 和 `ReplyRepositoryImpl.adjustLikeCount` 使用 `setSql("... + " + delta)`。目前调用方只传 `±1`，暂未形成可利用输入，但这种写法把安全约束藏在调用约定里，后续扩展容易引入非法 SQL 表达式。

建议：改为固定的 `+ 1` / `- 1` 分支或使用参数绑定，并增加计数不低于 0 的保护。
