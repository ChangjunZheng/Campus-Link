## 1. 问题陈述与目标

### 1.1 问题陈述

个人主页（F-ACC-002）当前按主 PRD 只展示"昵称、头像、学校/专业（选填）、签名、内容记录与统计"。对垂直校内社区而言，缺了两个**低成本、高上下文价值**的身份信息：

1. **年级/届别**：论坛里"同一届"是天然身份认同，也是回答的上下文——大一问环境配置、大四问秋招，回答者看一眼徽章就知道往哪答。而平台只对本校开放（学籍核验 P0 已保证学号真实），**学号前两位就是入学年级**（如 `249971346` → 24 级 → 2028 届），信息等于"白拿"，无需用户填写、无需名册加字段；
2. **想走的方向**：用户自选的技术/升学方向（如 Java 后端），帮助回答侧定向、增强面经求职版块的可信度（F-ACC-004 设置"已认证"标识的初衷即此），并为未来运营聚合提供数据（如"本站 40% 用户走 Java"）。

竞品参考：牛客个人中心的**身份卡结构**（身份徽章 + 方向/意向标签 + 创作数据一行）验证了这一信息结构的有效性；本设计只借鉴结构，不照搬其游戏化体系。

### 1.2 目标（本期结束时如何判定成功）

| # | 目标 | 度量方式（见第 6 节） |
|---|------|-------------------|
| G1 | 访问任何已认证用户主页，可见其级/届徽章 | 覆盖率 100%（推导规则内自动展示，无人工动作） |
| G2 | 用户主动标记方向，形成社区画像 | 方向标签填写率 ≥ 60%（内测期，占已注册用户） |
| G3 | 零隐私让步 | 学号原文 0 次出现在任何前台接口响应与页面中 |

**用户目标**：看主页的人快速获得"这是谁、哪一届、走什么方向"的上下文；被看的人零成本获得身份表达。
**业务目标**：回答定向更准（服务 48h 回复率）、面经版块可信度增强、为内容运营沉淀用户结构数据。

## 2. 非目标（Non-goals）

| # | 不做什么 | 为什么 |
|---|---------|--------|
| N1 | **不做等级 / 声望 / 排行等游戏化体系** | 归 F-GAME-001（主 PRD P2）；冷启动期做排行榜只会放大头部、打击新人，过早优化 |
| N2 | **不做完整求职意向表单**（期望城市 / 期望薪资 / 意向公司） | 单校内测期过重；且期望薪资涉及敏感信息，隐私评估成本大于价值 |
| N3 | **方向标签不做自由文本** | 自由文本必然长出小广告、脏数据、无法聚合；只允许预定义集合内选择 |
| N4 | **不展示学号原文，不做学号任何形式的可逆展示** | F-ACC-004 既有红线；本文所有展示均为**推导结果**（级/届徽章只暴露 2 位数字的语义，信息量远小于 9 位学号本身，且年级本就是半公开信息） |
| N5 | **不做用户主动纠偏年级的申诉/编辑流程** | 推导错误的个体（专升本等）属极少数，本期通过"规则核实 + 不显示兜底"处理（见 4.3 业务规则），纠偏流程等真实案例出现再评审 |
| N6 | **不在发帖页 / 帖子列表等处展示作者方向标签** | 本期只做主页场景；列表页加标签会显著增加视觉噪声，联动展示归 P2（见第 7 节 Q4） |

## 3. 用户与场景

### 3.1 用户故事

- 作为一名**大一学生**，我访问学长学姐的主页时想看到"24 级 · 2028 届"这样的徽章，以便判断对方的经验对我的年级是否有参考价值；
- 作为一名**准备找实习的大三学生**，我想在自己的主页标上"Java 后端"，以便回答者与同好快速识别我的方向，也让面经分享更有针对性；
- 作为一名**回答者**，我点进提问者主页想看到其年级与方向，以便用对方能理解的方式回答（大一讲步骤、大四讲取舍）；
- 作为一名**浏览面经版块的学生**，我希望作者主页的"已认证 + 级/届 + 方向"组合起来可信、可对照，以便判断这份面经对我的参考权重。

### 3.2 边界场景（必须覆盖）

- **无学号账号**（dev 管理员 `admin@campuslink.local`，bypass 门控账号）：不显示级/届徽章，其余正常；
- **学号前两位超出合理年份区间**（非 20~31，即 2020~2031 级之外）：视为编码不识别，**不显示徽章**，绝不显示错误信息；
- **未填写方向标签**：主页该区块整体不渲染（不留"未填写"占位），不引导访客催促填写；
- **本人编辑视角**：本人可见"编辑"入口；他人主页绝不出现编辑入口（越权防护走既有鉴权机制）；
- **学籍核验未通过 / 未注册用户**：无主页，不适用；
- **方向标签数量越界**（> 3 或选"未定"后又选其他）：提交时拒绝并提示字段级原因。

## 4. 功能需求

### 4.1 功能列表与优先级

| 编号 | 功能 | 优先级 | 模块 |
|------|------|:------:|------|
| F-ACC-005a | 级/届徽章（学号前两位推导展示） | **P0** | 账号 |
| F-ACC-005b | 方向标签（预定义集合选 1~3，本人可改） | **P0** | 账号 |
| F-ACC-005c | 方向标签填写率埋点 | P0 | 数据 |
| F-ACC-005d | 状态标签（求职准备中 / 考研中 / 在读） | P2 | 账号 |

### 4.2 交互说明

- **展示位置**：个人主页身份卡（头像 + 昵称右侧徽章行：`已认证`（F-ACC-004 既有）→ `24 级` → `2028 届` → `学校·专业`（F-ACC-002 选填，既有））；方向标签独立一行，胶囊样式；
- **编辑入口**：仅本人主页显示"编辑资料"，方向标签在其中以多选组件呈现（预定义集合，上限 3 个，可清空）；
- **视觉口径**：遵循 [ui-guideline](../设计/UI规范/界面规范.md) 的令牌与组件约定，徽章/胶囊不引入新的设计令牌。

### 4.3 功能详情与验收标准

**F-ACC-005a 级/届徽章（P0）**

- 描述：对**已通过学籍核验**的用户，由学号推导并在主页展示级/届。推导规则：学号 `^\d{9}$` 的**前两位** = 20yy 级入学年份后两位；**届别 = 20yy + 4**（按本科标准学制 4 年）。
- 业务规则：
  - 推导为**读时计算**（domain 值对象职责），不落库、不新增迁移；
  - 前两位不在 20~31 区间 → 不识别，不显示徽章；
  - 无学号账号不显示徽章；
  - **学号原文不出现在任何对外响应中**（接口只返回推导出的 `gradeEnroll: 24` / `gradeGraduate: 2028`，或不返回）；
  - ⚠️ **编码规则前提待核实（见第 7 节 Q1）**：专升本 / 留级同学是否同样符合"前两位 = 入学年"？**Q1 未确认前，届别徽章标注口径为"推定"的内部实现细节、页面上不做免责声明**；若 Q1 确认存在"+2 年制"等混合编码，届别徽章降级为**仅展示"级"**（P0 范围相应收窄，决策点在评审时定）。

```gherkin
Given 已通过学籍核验且学号为 249971346 的用户
When 任意用户访问其个人主页
Then 身份卡展示徽章"24 级"与"2028 届"，且页面与接口响应中不出现学号原文

Given dev 管理员账号（无学号，bypass 门控）
When 访问其主页
Then 不显示级/届徽章，页面无错误

Given 某用户学号前两位为 88（不在 20~31 区间）
When 访问其主页
Then 不显示级/届徽章，页面无错误

Given 已登录用户访问他人主页
When 查看身份卡
Then 不存在任何编辑入口；本人访问自己的主页时可见"编辑资料"入口
```

**F-ACC-005b 方向标签（P0）**

- 描述：用户在**预定义标签集**中选择 1~3 个"想走的方向"，展示于主页；本人可随时增删改。
- 预定义标签集（v0.1 提案，终稿见开放问题 Q3）：`Java 后端` / `前端` / `C/C++` / `Python` / `AI·算法` / `大数据` / `嵌入式` / `测试` / `运维·网安` / `考研` / `考公·国企` / `未定`。
- 业务规则：
  - 集合**服务端枚举硬编码 + 配置可扩展**，前端不下发自由输入能力；新增标签走配置变更（不走代码发布）；
  - 数量 1~3，`未定`与其他标签互斥；选择即公开（无独立可见性开关——单校社区、信息本身非敏感）；
  - 存储归账号上下文（用户资料扩展），照抄 `module/account` 四层结构，ArchUnit 自动覆盖。

```gherkin
Given 已登录用户在编辑资料页
When 勾选"Java 后端""AI·算法"并保存
Then 主页方向标签行展示这两个标签，统计埋点 direction_saved 上报

Given 已登录用户尝试选择第 4 个标签
When 提交
Then 拒绝并提示"最多选择 3 个方向"，已有选择不变

Given 用户已选"未定"
When 再次勾选"Java 后端"
Then "未定"被自动取消（互斥），保存成功

Given 用户清空全部方向标签并保存
When 访问其主页
Then 方向标签行整体不渲染
```

**F-ACC-005c 埋点（P0）**

| 事件 | 触发时机 | 关键属性 | 支撑指标 |
|------|---------|---------|---------|
| direction_saved | 方向标签保存成功（含清空） | 标签列表、变更前后数量 | 填写率（G2） |
| profile_view | 主页访问（会话去重） | 被访者是否有徽章/标签 | 展示渗透、徽章覆盖率（G1） |

## 5. 成功指标

| 指标 | 定义 | 目标 | 评估时点 |
|------|------|------|---------|
| 徽章覆盖率 | 有学号且编码可识别的用户主页中，徽章正常展示的比例 | 100%（纯推导，不达标即缺陷） | 上线即验 |
| 方向标签填写率 | 已选 ≥ 1 个标签的用户 / 全部注册用户 | ≥ 60%（内测期） | 内测 ≥ 1 周 |
| 标签分布可用性 | top1 标签占比 < 80%（说明集合区分度够，不是人人标同一个） | 观察项 | 开放注册 2 周 |

> 本功能属**信息展示类**，不设强业务指标；其价值经由回答定向与面经可信度间接体现（观察 48h 回复率不倒退即可）。

## 6. 技术约束与依赖（供设计阶段输入）

- **推导纯函数化**：级/届推导放 `module/account` domain 值对象（`StudentId → gradeEnroll/gradeGraduate`），**零迁移、零落库**；
- **方向标签存储**：账号上下文用户资料扩展（预计 1 张 `user_direction` 表或主表 JSON 列，设计阶段定，走 `V<n>__` 迁移）；
- **契约**：主页读接口返回增加徽章字段；编辑接口归 F-ACC-002 本体的资料编辑能力——**若个人主页本体尚未开工，本增强与其合并设计，不单独造接口**；
- **依赖**：Q1（编码规则核实）阻塞**届别**徽章定稿，不阻塞"级"徽章与方向标签。
