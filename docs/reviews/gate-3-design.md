## 2. 评审形式与手册要求的差异

| 项 | 手册要求 | 实际执行 |
|---|---------|---------|
| 组织形式 | 技术方案评审会，**架构师主持**，对齐 PRD 与 UI 稿（3.3 节关键活动 4） | 未召开会议；发起人单人简化评审 |
| 参与角色数 | ≥ 2 名不同角色（第 2 节） | 1 人 |
| 评审覆盖版本 | 提交评审的版本 | **仅 v0.1 经过评审**。v0.2 自述"设计评审会补充确认"（实际无会议，为发起人同日决议）；v0.3（JDK 21 + Boot 4.1）、v0.4（**账号上下文 DDD 四层重构，ADR-012**）**从未经任何形式评审** |
| 纪要归档 | 归档至 `docs/`（4.1 节） | 当时未归档，本文件为补录 |

> **本节最重要的一条**：v0.4 的 DDD 重构不仅已评审缺失，而且**已落地实现**（`module/account` 四层目录已存在，14/14 单测通过）。即"先改代码、后无评审"，与手册 3.3"开发可直接依据文档开工"的意图相反——文档是在实现之后追写的。

## 5. 补录时核出的内部矛盾与事实错误

以下均已在 2026-09-11 对照代码实际状态核实：

| # | 位置 | 问题 | 严重度 |
|---|------|------|:-----:|
| D-1 | §2.4 末"包命名约定" | 写"`module` 下每个业务模块按 `controller` / `service` / `mapper` / `entity` / `dto` / `vo` 分包；跨模块调用只允许通过 `service` 接口"——**与 ADR-012 的 domain/application/infrastructure/web 四层、与 AGENTS.md 完全冲突**。实际代码为四层（`module/account/{domain,application,infrastructure,web}` 已存在）。后续 board/post 上下文若照此段开发会写出错误结构 | **高** |
| D-2 | §3 模块表 | 仍列 auth / roster / user 三个独立模块，仅在表下追加"v0.4 注"说明已合并为 account 上下文 → 同一文档内两套描述并存 | 中 |
| D-3 | §4.3 时序图 | 参与者仍为"auth 模块""roster 模块"，未随 DDD 重构更新 | 低 |
| D-4 | §4.2 | "完整 DDL 在 `backend/sql/schema.sql`"——实际文件为 `backend/sql/01_schema.sql`（另有 `02_seed_boards.sql`） | 低 |
| D-5 | §7.3 | 引用"流程手册发布清单第 7 项"——流程手册无发布清单，第 7 项实际在 [发布检查清单模板](../templates/release-checklist-template.md) §2（内容对应正确，指向错误） | 低 |
| D-6 | §2.4 目录树 | ASCII 排版破损：backend 的 `config/` 行与 frontend 的 `vite.config.ts` 挤在同一行，树形层级错位，渲染后不可读 | 中 |
| D-7 | §2.2 标题 | "技术选型（v0.3 更新）"但表内含 v0.4 信息；标题内嵌版本号会随迭代持续腐化 | 低 |

### 已核实为正确的部分（正向确认）

- **接口契约与代码实现一致**：`POST /api/v1/auth/{verify-student, captcha, register, login}`、`POST /api/v1/admin/roster/import`、`GET /api/v1/users/me` 六个端点与 §5 清单逐一对应 → ADR-012 宣称的"对外 API 契约不变"**属实**；
- **安全设计具体可测**：白名单到标签级、`APP_HASH_KEY` / `APP_CRYPT_KEY` 密钥分离、名册不落明文学号、三种核验失败统一提示防枚举、IP 10 次/小时限流、机审 **fail-closed**（明确禁止 fail-open）；
- **裁剪留痕规范**：ADR-008 明确引用手册 5.1 说明 test 环境并入 staging——裁剪有依据、有出处，符合手册精神。

## 6. 评审结论

**有条件通过**（维持技术方案头部原结论），但**附加条件已扩大**：

1. 原行动项（UI 稿）至今未闭环；
2. **新增**：v0.3、v0.4 两次重大技术变更（含已落地的 DDD 重构）须补充设计评审或发起人书面确认；
3. **新增**：D-1 属误导性内容，须在 Sprint 2 开工前修正（否则后续上下文按错误约定开发）。

> 手册第 3 章明确："评审门未通过（或未形成'有条件通过'闭环）前，不得开始下一阶段工作"；4.1 明确："'有条件通过'的行动项未闭环前，不得视为该门通过"。**据此，阶段四开发在程序上不应启动，但实际已启动并完成 Sprint 1（T1~T9）**。该程序偏离须在 [裁剪与让步放行记录](../tailoring-waivers.md) W-02 签署让步放行。
